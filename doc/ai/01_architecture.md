# Architecture & Design Decisions

> Practical "how do I run and debug this on the real robot" notes live in `06_hw_testing_guide.md`,
> not here. This file is the stable design/rationale reference.

## Package Overview
* **`istrorsx_hw`** — ROS 2 hardware integration wrappers for the legacy control board, GPS, lidar, and camera (`ctrlboard_node`/`gps_node`/`lidar_node`/`camera_node`).
* **`istrobtx`** — shared legacy scaffold (`Config`, `DataSet`, `Threads`, `Logger`, `mtime`, `system`, `GeoCalc`, plus a few small hardware-independent utility headers) used by every node in both `istrorsx_hw` and `istrorsx_core`. Not a ROS interface package (no `.msg` files) — a plain C++ library package.
* **`istrorsx_core`** — navigation, vision, and control logic ported from `istro_rt2025.cpp` (currently: `drive_node`, `navigation_node`, `vision_node`, `planner_node`, `keyboard_node`, `save_node`, `telemetry_node`; see "Planned Package Split" below for what's still to come).
* **`make_clean.sh`** (workspace root) — removes everything `colcon build` regenerates (`build/`, `install/`, `log/`) plus this project's own runtime `logout/`/`out/` dirs (re-created empty afterward, since node startup code expects them to already exist — see `04_installation.md` — and doesn't create them itself). Meant to be run before backing up the whole workspace, to keep the backup small; does not touch `src/`, `conf/`, or anything under `script/` (venvs/model files aren't `colcon build` output and aren't trivially regenerable without network access).
* **`istrorsx_nn`** — the neural-network TCP client this was meant to be (`VISIONN_HELLO`/`VISIONN_IMPRQ`/`VISIONN_IMPRS`, see "NN Inference Service" below) is already built, just not factored out into its own package: `visionn.cpp`/`VisioNN` is linked directly into `vision_node` (its only consumer, `VISION_NODE_SOURCES` in `istrorsx_core/CMakeLists.txt`). Splitting it into a real `istrorsx_nn` package is a **future idea, out of scope of this migration** — worth doing if a second NN-consuming node ever exists, not needed for `vision_node` to work today.
* **`istrorsx_bringup`** — built (2026-08-29): one `full.launch.py` bringing up the whole system at once, replacing the legacy `main()`/`loop()`'s `threads.start(...)` orchestration. See its own section below.
* **AHRS — marked obsolete, not being migrated.** No `AhrsDevice`/`ahrs_node` exists or is planned: this project has no physical AHRS unit available to test against, so there's nothing to verify a port against. `Config`'s own `useAHRSystem`/`AHRSystemPortName` fields and `-ahrs <device>` CLI flag (`config.cpp`) are kept only because they're part of legacy's own CLI surface being parsed faithfully — they're dead weight beyond that, default off, no code path acts on them. `planner_node.cpp`'s `NOT_YET_MIGRATED` tag for legacy's `ahrs_yaw`/`gps_lastp_azimuth` yaw fallback needs no further action for the same reason (that fallback was already dead/commented-out code in `istro_rt2025.cpp` itself, confirmed during `planner_node`'s own design pass — not a real gap even before AHRS being ruled out).
* **Framework & Version:** ROS 2 Jazzy, C++ (C++17)

## `istrobtx` — Shared Legacy Scaffold
* Split out of `istrorsx_hw` into its own package because `drive_node` (`istrorsx_core`) needed the exact same `Config`/`DataSet`/`Threads`/`Logger`/`mtime`/`system` scaffold every `istrorsx_hw` node already shared internally — rather than either duplicating those 6 files into a second copy (rejected: risks the two copies drifting apart, the same failure mode already seen once with `lidar_rplidar.cpp`) or having `istrorsx_core` reach into `istrorsx_hw`'s private source tree by relative path (rejected: backwards/fragile package coupling). A real `ament_cmake` library package, built once as a static library and linked by both `istrorsx_hw`'s four executables and `istrorsx_core`'s `drive_node`.
* Headers install flat (`include/config.h`, not `include/istrobtx/config.h`) so every consumer keeps the project's established **bare-include convention** (`#include "config.h"`, not a package-prefixed path) — matches how these files were already included everywhere before the split. This does mean `istrobtx`'s header names (`config.h`, `system.h`, ...) are generic and could collide with another package's flat includes; acceptable for this project's size/scope, not meant to generalize beyond it.
* Only the hardware-**independent** scaffold moved here. Hardware-specific code (`ControlBoard`, `GpsDevice`/`GeoCalc`, `Lidar`, `Camera`, and their `istro_main_<subsystem>` scaffolds) stays in `istrorsx_hw`, each with its own external SDK dependency (`libgps`, `rplidar_sdk`, `librealsense2`) that `istrobtx` must **not** pull in.
* Two small extractions were needed to keep that boundary clean, since `DataSet`/`Config::Config()` originally reached into hardware-specific headers just for a few plain data types/constants:
  * **`lidar_defs.h`/`.cpp`** (`LIDAR_DATA_NUM`, `lidar_data_t`, the `LIDAR_DISTANCE_*`/`LIDAR_QUALITY_*`/`LIDAR_STOP_*` calibration constants, and the free functions `lidar_process()`/`lidar_draw_output()`) — split out of `istrorsx_hw`'s `lidar.h`/`.cpp`, which `DataSet` needs for its `lidar_data` member but which otherwise pulls in the RPLIDAR SDK unconditionally (`ISTRO_RPLIDAR` is always defined). `lidar.h` itself (the `Lidar` class, SDK-dependent: connect/init/close/`getData()`) stays in `istrorsx_hw` and now includes `lidar_defs.h` instead of defining any of this itself. **Side benefit:** `ctrlboard_node`/`gps_node`/`camera_node` no longer need `RPLIDAR_SDK_INCLUDE_DIR` on their include path at all anymore — only `lidar_node` does, since only it still includes the full `lidar.h`. **`lidar_process()`** is a 1:1 port of legacy `Lidar::process()` (`istro_rt2025.cpp`, called from `process_thread`), converted from a class method to a free function since it never touched `Lidar`'s own instance state — it was dead code in `istrorsx_hw` (no caller there; `lidar_node` only captures/publishes raw scans) until `planner_node` needed to call it without the SDK, at which point it moved here (`01_architecture.md` § `planner_node` decision #2). **`lidar_draw_output()`** (2026-08-29) is the same treatment for legacy `Lidar::drawOutput()` (called from `save_thread` only) — also never touched `Lidar`'s own instance state, moved here so the future `save_node` can render the `lidar.png` debug overlay without linking the RPLIDAR SDK. Originally named `lidar_types.h` (types only); renamed/merged with the later `process()`/`drawOutput()` extractions into one `lidar_defs.h`/`.cpp` pair, per a project-wide convention: use `xxx_defs.h`/`.cpp` consistently for a subsystem's shared-but-hardware-independent pieces, not a mix of `_types`/`_obst`-style names (see the `ctrlboard_defs.h` entry below, merged the same way for the same reason).
  * **`camera_defs.h`/`.cpp`** (`CAMERA_DEPTH_FRAME_WIDTH`/`HEIGHT`, and — since 2026-08-29 — the free function `camera_draw_depth_frame()`) — same split, out of `istrorsx_hw`'s `camera.h`/`.cpp` (`librealsense2`-coupled). The constants are needed by `istrorsx_core`'s `vision_depth.h` for the depth-obstacle arrays' fixed size; `camera.h` itself now includes `camera_defs.h` instead of defining these itself. **`camera_draw_depth_frame()`** is a 1:1 port of legacy `Camera::drawDepthFrame()` (called from `save_thread` only, for the `cdepth`/`rcdepth` debug images) — like `lidar_draw_output()`, it never touched `Camera`'s own `librealsense2` handles (only `this->device_id`, now an explicit parameter, used solely for a side JSON debug dump's own field). `Camera::drawFrame()` (also `save_thread`-only, for `camera`/`rcamera`) was checked too and is **not** extracted — its actual body is a no-op outside `ISTRO_GUI` (`imshow()` only, no calibration overlay of any kind exists to reproduce), so `camera.jpg` in this port is simply the raw, unmodified frame. Originally named `camera_types.h` (constants only); renamed/merged with the `drawDepthFrame()` extraction into one `camera_defs.h`/`.cpp` pair, same convention as `lidar_defs.h` above.
  * **`ctrlboard_defs.h`/`.cpp`** (`SA_*`/`VEL_*`/`CTRLB_STATE_*`/`CTRLB_LED_PROGRAM_*`, and `ctrlb_obstState()`) — split out of `istrorsx_hw`'s `ctrlboard.h`/`ctrlboard.cpp`. `Config::Config()` needs `VEL_ZERO`/`VEL_OPT`/`VEL_BACK` for its default velocities, and `drive_node` needs the full obstacle-priority set (`CTRLB_STATE_OBSTACLE`, `ctrlb_obstState()`) to port `loop()`'s AUTONOMOUS branch faithfully — neither needs the `ControlBoard` class or serial I/O itself. `ctrlboard.h` now includes `ctrlboard_defs.h` instead of declaring any of this itself. `ctrlb_obstState()` originally lived in a separate `ctrlboard_obst.h`/`.cpp` pair; merged into `ctrlboard_defs.h`/`.cpp` (2026-08-27) as part of a project-wide naming cleanup — see the `lidar_defs.h` entry above for the same merge and its rationale.
  * **`event_defs.h`** (2026-08-29, header-only, no `.cpp`) — not a hardware-independence split like the three above, a new single-purpose file: `#define EVENT_TAG "rt2026"`, the short file-naming tag for whichever competition this codebase is currently being prepared for, used everywhere a filename needs it (`save_node.cpp`'s `saveImage()`/`saveNavMap()`, `telemetry_node.cpp`'s `LOG_FNAME`/`GZIP_CMD`/output filenames) via adjacent-string-literal concatenation (`EVENT_TAG "_%07u_..."`, `"istro_" EVENT_TAG ".log"`), so changing the competition means editing this one `#define`. Found via a project-wide grep for literal `"rt2025"` occurrences — most turned out to be comments referencing the legacy source file `istro_rt2025.cpp` by name (a permanent historical filename, unrelated to which competition is current, deliberately left alone) rather than actual filename-building code; six real ones were centralized. **Named `EVENT_TAG`, not `RT_TAG`**: "RT" specifically means Robotour, but this project's robot also competes at events with different short codes (RR = Robotem Rovne, RO = RoboOrienteering, ...) — the letters themselves change across events, not just the year, so the constant's own name can't bake in one specific competition's initials. **One real limit, documented in both places**: `conf/log4cxx.xml`'s own `<param name="file"/>`/`FileNamePattern` (the filename log4cxx itself actually writes to) is a separate XML file the C preprocessor can't reach — its log file name must still be updated by hand alongside `EVENT_TAG`, or `telemetry_node`'s `LOG_FNAME`/`GZIP_CMD` will silently point at a file log4cxx never writes to.
  * The same calibration values are *also* declared as message constants in `istrorsx_hw/msg/SpeedCommand.msg` (`SA_STRAIGHT`/`SA_MIN`/`SA_MAX`/`VEL_ZERO`) and `istrorsx_hw/msg/ServoData.msg` (`STATE_*`), for ROS-message-only consumers that don't link `istrobtx` — a deliberate, documented duplication (message-wire-format constants vs. compile-time C++ constants serve different consumers with different lifecycles), not an oversight; keep both in sync if these values ever change.
* **`GeoCalc`** (`geocalc.h`/`.cpp`, GeographicLib-based distance/azimuth/coordinate math) moved here from `istrorsx_hw` once `navigation_node` needed it too — it has no hardware dependency (only `GeographicLib`, found via pkg-config, exported `PUBLIC` from `istrobtx`), so unlike `GpsDevice` it didn't need to stay behind. `istrorsx_hw`'s `gps_node` and `istrorsx_core`'s `navigation_node` each construct and own their own `GeoCalc geoCalc;` instance (separate processes, no shared state) — only the class definition is shared.
* **`DegreeMap`** (`dmap.h`/`.cpp`) moved here from `istrorsx_hw` (was private to `lidar.h`/`lidar_node`) once `vision_node`'s port needed it too (`Vision`/`VisionDepth`'s `eval()` all produce/consume `DegreeMap`s) — zero dependencies (`<string>` only), the simplest of these moves. `lidar_node`'s own `#include "dmap.h"` needed no change (already a bare include).

## `drive_node` (`istrorsx_core`) — Drive/Arbitration Node (renamed from `control_node`)
* A **1:1 port** of `istro_rt2025.cpp`'s `prog_start()`/`prog_stop()`/`prog_loop()`, `loop_waitKey()`, `loop_readData()`, and `loop()` — unlike every other node so far, this one deliberately keeps the legacy control flow and variable names/shapes recognizable rather than redesigning around ROS idioms, per project decision.
* **Reuses the legacy `Threads`/`DataSet` shared-state pattern for real**, not just as a vestigial write-back like the other nodes: incoming ROS messages (`ServoData`, `GpsData`, `DriveCommand`) are first written into `drive_node`'s own process-local `DataSet` via `servo_writeData()`/`gps_writeData()`/`drive_writeData()` (free functions, mirror `ctrlBoard_writeData()`/`gps_writeData()` in the other nodes), and `loopReadData()` then reads them back out of `THDATA_STATE_SHARED` — exactly the same two-step the legacy single-process app did, even though here it's read back out of the same process's own memory it was just written into. Each `*_writeData()` stores the fields the corresponding `.msg` actually carries; fields `DataSet` has that the message doesn't (e.g. `ServoData` doesn't carry `ctrlb_euler_*`/`ctrlb_calib_*` — those are `ImuData`'s) are left at their constructor defaults, not invented.
* `loop()`'s blocking `for(;;)` becomes a 20 Hz ROS wall timer (`controlTick()`, one call = one legacy loop iteration). `threads.start(...)` (which would spawn the legacy capture/vision/process/etc. pthreads) is never called — same pattern as every `istrorsx_hw` node, since those subsystems either don't exist yet or are separate ROS nodes now.
* **Manual input is `sensor_msgs/msg/Joy`, not a custom message** — a deliberate, later exception to the project's general "no external ROS 2 packages, only our own legacy-derived messages" rule (see `doc/ai/03_progress.md`), made specifically so a real gamepad (via the standard `joy` package) and `keyboard_node` (see below) can both drive `drive_node` through the exact same topic/format without `drive_node` needing to know which one is talking. `pollKey()` derives a legacy-style key char from the latest `Joy` message every tick, replacing `cv::waitKey()`: **buttons are edge-triggered** (one `pending_key_` event per physical press, set in `cb_joy()`, consumed once by `pollKey()`) matching a real keypress's one-shot nature, while **axes are level-triggered** (read fresh every tick, fire their mapped key continuously while deflected past a deadzone) matching how a joystick axis naturally behaves. The exact `axes[]`/`buttons[]` index mapping (Xbox physical layout for axes/buttons 0-7, synthetic `buttons[10..22]` for keys no physical gamepad has enough buttons for: the legacy `'0'`-`'9'` absolute-velocity presets, `'g'` GPS-point debug print, and `'q'`/`'e'` full-lock steering) is `drive_node`'s own wire contract, `public` on the class (not a private implementation detail, since `keyboard_node` needs the same indices) — see `drive_node.hpp`'s `JOY_*` constants. `'q'`/`'e'` are buttons rather than extreme axis values because legacy sets `steering_angle` once per press (`SA_MAX`/`SA_MIN`), not a continuous increment like `'w'`/`'s'` — a real gamepad's own full stick deflection still independently reaches the same result through `pollKey()`'s pre-existing axis-threshold check, unchanged; the button is an additional path, not a replacement.
  * **Corrected 2026-09-10, real-hardware session:** the axis-threshold nudge model above (`'a'`/`'d'`/`'w'`/`'s'`, `steering_angle`/`velocity` incrementing per tick while past a deadzone) turned out fine for `keyboard_node`'s synthetic axis (a key has no "position" to return to) but wrong for a **real** gamepad: releasing the stick to center never fires any key, so `steering_angle`/`velocity` just held their last value instead of returning to `SA_STRAIGHT`/`VEL_ZERO` — the robot kept turning, and kept driving, after the stick was released. Fixed with two new methods, `applyJoystickSteering()`/`applyJoystickThrottle()` (`drive_node.cpp`), called once per `controlTick()` alongside `loopWaitKey()`: for a **real** gamepad only, they map the raw axis value proportionally onto `[SA_MIN, SA_MAX]` / `[VEL_ZERO+joystick_velocity_max_back, VEL_ZERO+joystick_velocity_max_fwd]` instead, so center means exactly `SA_STRAIGHT`/`VEL_ZERO` by construction. `keyboard_node`'s own nudge behavior is untouched (explicit user call — "cez klávesnicu to vieme normálne ovládať"), which needed a new way to tell the two `Joy` sources apart on the same topic/axes: `JOY_BUTTON_SOURCE_KEYBOARD` (button `23`), always set by `keyboard_node`, never reachable by a real pad — checked via the new `isKeyboardJoy()` helper, which `pollKey()`'s own axis-threshold checks are now gated behind too (real-gamepad axes no longer produce `'a'`/`'d'`/`'q'`/`'e'`/`'w'`/`'s'` at all, fully replaced by the two new methods for that source).
    A second, hardware-specific issue surfaced while verifying this live: the Xbox pad has steering and throttle on the *same* physical stick, and there is **no closed-loop speed feedback** to the ESC (it applies whatever raw value it's sent, immediately) — so a mostly-lateral steering motion's small forward/back component was enough to launch the robot. Fixed with three new `drive_node` ROS params (declared in the constructor, mirroring `telemetry_node.cpp`'s `declare_parameter` pattern, wired into `full.launch.py` the same way `xbox_deadzone_arg` already wires `joy_node`'s own deadzone): `joystick_velocity_max_fwd`/`joystick_velocity_max_back` (default `12`/`-17`, the offsets from `VEL_ZERO` — also double as `applyJoystickThrottle()`'s proportional range endpoints) and `joystick_throttle_deadzone` (default `0.5`, wider than steering's `0.3`/`0.05`, gating `pollKey()`'s throttle block and `applyJoystickThrottle()`'s take-over threshold). All three are real-joystick-only, same `isKeyboardJoy()` scoping — `AUTONOMOUS`/`progLoop()`'s own competition-speed driving is untouched.
* Every legacy `ctrlBoard.setXxx()`/`displayText()`/`setBallDrop()` call site becomes a `publishXxx()` helper that publishes the equivalent `SpeedCommand`/`LedConfig`/`DeviceAction` message **at that same point** in the ported control flow, rather than being batched into one message per tick — `controlTick()` can and does publish multiple `SpeedCommand` messages in one tick (e.g. one for `setSpeed`, one for `setSteeringAngle`) exactly where legacy made two separate `ctrlBoard` calls. `conf.useControlBoard` guards around each legacy call site were dropped (not ported) — that guard existed because the legacy single-process app might not have a `ControlBoard` instance at all; `drive_node` always publishes regardless of whether `ctrlboard_node` happens to be running, since ROS pub/sub doesn't require a subscriber to exist.
* The legacy loop()-local `int prog_stop` variable — which shadowed the free function `prog_stop()` in the original C++ (legal for a local variable to hide a free function name) — is `prog_stop_flag_` here, since both the state and the `progStop()` method are class members and can't share a name.
* **Not yet ported**, left as explicit gaps (see `doc/ai/03_progress.md` backlog): the force-wrongway `loopWaitKey()` branch has a Joy mapping but the flag itself has no consumer in `planner_node` yet (see `planner_node`'s own matching `NOT_YET_MIGRATED` tag); `ctrlb_obstState()`'s exact obstacle-priority/timeout semantics are reused as-is via `istrobtx`, unchanged from `ctrlboard.cpp`'s original. `'0'`-`'9'`/`'g'`/`'q'`/`'e'` (synthetic buttons `[10..22]`, no physical gamepad has enough buttons) are now reachable from `keyboard_node` — see below.

## `keyboard_node` (`istrorsx_core`) — Keyboard Manual-Input Publisher
**Built.** Replaces legacy `loop_waitKey()`'s `cv::waitKey()`-based key detection (which needed an X11 OpenCV window, and therefore a VNC connection on a headless robot) with a plain terminal-raw-mode reader running in whatever terminal the node was launched from — no GUI/VNC needed. Publishes `sensor_msgs/msg/Joy` on the same `/joy` topic `xbox_controller_run.sh`'s `joy_node` would, using `drive_node.hpp`'s own `JOY_AXIS_*`/`JOY_BUTTON_*` constants (now `public`, since a second node needs to read them) — `drive_node` doesn't need to know which one is talking. Not a port of any legacy thread's own `Config`/`Threads`/`DataSet` startup scaffold (no `istro_main_keyboard.cpp`/`.h`) — this functionality has no legacy 1:1 counterpart (legacy used a GUI window, not a terminal), so it's a plain, standalone `rclcpp` node.

* **No key-up event over a plain terminal** (unlike X11/evdev) — holding a key down only produces repeated keydown bytes at the OS's own auto-repeat cadence (a real initial delay, commonly a few hundred ms, before a faster steady-state repeat rate). To present this as a continuously-held axis/button the way a real joystick would, a background thread (raw-mode `termios`, `VMIN=0`/`VTIME=1` so `read()` returns every ~100ms even with no input, letting the thread notice shutdown promptly) records the last-seen time of each mapped key; a fixed-rate publish timer (100ms / 10Hz) treats a key as "still held" if seen within the last 500ms — long enough to bridge the OS's own initial-repeat-delay gap, short enough that release is still detected promptly, and entirely decoupled from the terminal's own irregular repeat timing.
* **Axes vs. buttons chosen per legacy semantics, not just "movement vs. action"**: `'a'`/`'d'` (nudge) are genuinely partial values (legacy: `steering_angle += 10`, an increment), so they stay axis-based (`0.5`/`-0.5`), matching a real joystick's natural partial deflection. `'q'`/`'e'` (full-lock) set `steering_angle` to a fixed `SA_MAX`/`SA_MIN` **once** per press, not a continuous change — closer to a legacy one-shot action than a continuous quantity — so they're dedicated buttons (`JOY_BUTTON_STEER_FULL_LEFT`/`RIGHT`), routed through `drive_node`'s existing `cb_joy()` edge-detection (`pending_key_`) unchanged. `'w'`/`'s'` (genuine increments, like `'a'`/`'d'`) stay axis-based, matching `drive_node`'s pre-existing `pollKey()` design (already built before this node existed).
* **Terminal display**: prints `'<key>' -> <what it does>` to `stdout` on the press edge only (not every repeat/tick) — a direct `std::cout` print, not routed through the project's `log4cxx`-based `LOGM_*` logger, since this is live operator feedback in the same terminal the user is typing into, not a log record to correlate later.
* **`'g'` (GPS-point debug print) now has a mapping** — previously flagged as "low-value enough to skip" when only a physical gamepad (finite buttons) was the only real input device; a keyboard has no such limit, so it's `JOY_BUTTON_GPS_DEBUG` (button `20`).
* **ESC/`'x'`/`'X'` are handled locally** (exit this node's own process) — not forwarded as a Joy message; letting a stray keypress on a remote terminal tell `drive_node` itself to shut down would be an odd, risky side channel.
* **Verified end-to-end** with a `pty`-based test (`rclpy` subscriber on `/joy` + simulated keystrokes written into a real pseudo-terminal, so the actual `termios` raw-mode code path runs, not just a plain pipe): held `'w'` → `axes[THROTTLE]=+1.0`, release → returns to `0.0` after the hold-timeout; single `'q'` → `JOY_BUTTON_STEER_FULL_LEFT=1` with the steering axis left untouched at `0.0` (confirms the button-not-axis design); space/digit `'7'` → the correct button indices; held `'a'` → `axes[STEERING]=0.5`; `ESC` → clean process exit (code `0`) with the terminal properly restored (no hang, no leftover shell corruption). No leftover process after exit.
* Needs `std::thread` (background terminal reader) → links `Threads::Threads` (`find_package(Threads REQUIRED)`, `CMakeLists.txt`).

## `navigation_node` (`istrorsx_core`) — Navigation/Route Node
* A **1:1 port** of `istro_rt2025.cpp`'s `gps_thread()`'s navigation-point/route-planning extension (`navig.cpp`/`navmap.cpp`) — the part of `gps_thread` NOT already ported into `istrorsx_hw`'s `gps_node` (fix acquisition, last-fix distance/azimuth, `gps_pt[]` history all stay there). Legacy ran this in the same loop iteration as the physical GPS read; now that `gps_node` (device polling) and `navigation_node` (this) are separate processes, `navigation_node` instead reacts to `gps_node`'s published `/robot/gps_data`, once per message.
* **`navig.h`/`navig.cpp`, `navig_data.h`/`navig_data.cpp`, `navmap.h`/`navmap.cpp`, `navmap_data.h`/`navmap_data.cpp` live in `istrorsx_core/include/istrorsx_core/istrobtx`/`istrorsx_core/src/istrobtx`** (not the shared `istrobtx` package) — analysis of every call site in `istro_rt2025.cpp` found exactly one caller outside `gps_thread` (`navigation_point_set()`, called from `process_thread`'s `loadarea_process()` when a QR scan lands a coordinate — see gap below); everything else is exclusive to `gps_thread`/`navigation_node`. Since `navigation_node` and the future `planner_node` both live in `istrorsx_core` (same package), there's no cross-package boundary forcing these headers to be shared the way `istrobtx` is — a future `planner_node` can just `#include "istrorsx_core/istrobtx/navig.h"` directly.
* `navmap_data.cpp`/`navig_data.cpp` are large, mostly-generated static data tables (per-park GPS graphs and named waypoints, selected at compile time by `system.h`'s `ISTRO_MAP_*` switch, currently `ISTRO_MAP_BA_SADJK` — "Sad Janka Krala", Bratislava) — copied verbatim, no edits.
* `navmap.cpp`'s `navmap_load()` (`.osm` XML import, `ISTRO_LIBXML2`) is never used for navigation — `navmap_init()` always uses the compiled-in `navmap_import_data()`. Its only caller is the `NavMapExport` service below. `navmap_init()` also unconditionally calls `navmap_export_kml("out/navmap-export.kml")` at startup (a pre-existing legacy `"out/"`-relative-path convention, same as the not-yet-built `save_node`'s image dumps) — non-fatal if `out/` doesn't exist (return value ignored, matching legacy), but a workspace-root `out/` directory should exist before running this node.
* **Follows the cross-process `DataSet` round-trip pattern** (see `doc/ai/05_migration_guide.md`): `cb_gps()` writes the incoming fix into `navigation_node`'s own `DataSet` via `gps_writeData()`; `navigationTick()` (one call = one legacy `gps_thread` `while(1)` iteration) opens by reading it back via `navigation_readData()` (not `loopReadData()` — that name is reserved for `loop()`'s own port in `drive_node`), runs the ported computation, writes the results (`gps_navp_*`/`gps_ref`/`gps_x`/`gps_y`) back with `navigation_writeData()`, and publishes `NavigationData.msg` via a plain `publishNavigationData()` helper (parameters only, no `DataSet` access — it has no legacy counterpart to mirror). All three `*Data()` functions return `int` (`0`/`<0`), and every call site checks it and aborts on failure, matching legacy.
* Only the navigation-point/route state that must survive across separate `/robot/gps_data` messages (e.g. `navp_idx_`, the running route, `gps_navp_maxdist_`/`mindist_`, `nmap_np_idx_`) are `NavigationNode` members; everything legacy fully reassigned every `gps_thread` iteration regardless of fix status (`gps_fix`, `gps_latitude`/`longitude`(_raw), `gps_ref`) is a local inside `navigationTick()` instead. `coneseek_stop`/`coneseek_intlen` are also locals inside `navigationTick()`, but seeded from `coneseek_stop_`/`coneseek_intlen_` members — those *do* need to persist, since they're cached from `planner_node`'s `PlannerData.msg` (`ISTRO_VISION_ORANGECONE` mode only), published on its own independent 20ms schedule rather than once per `navigationTick()` call.
* **`/robot/navmap_export` service (`NavMapExport.srv`)** — port of legacy `navmap_test()`, which was a compile-time `#ifdef ISTRO_MAP_*` block (commented out in `main()`). The map name now comes from the request instead:
  * `map_name` `navmap-ba-sadjk` (a trailing `.osm` is accepted) → reads `conf/navmap-ba-sadjk.osm`, writes `out/navmap-ba-sadjk.kml` and `out/navmap-ba-sadjk.cpp` (a `navmap_import_data()` body, the same format as the blocks in `navmap_data.cpp`). Paths are relative to the node's working directory, the workspace root.
  * `navmap_load()` → `navmap_export_kml()` → `navmap_export_data()`, unchanged from legacy; response carries `success`, `message`, the three paths and the loaded `node_cnt`/`segment_cnt`.
  * **The live map is preserved**: `navmap_load()` overwrites `navMapNode[]`/`navMapSegment[]` — the arrays navigation is routing on, temporary route nodes included — so the handler copies them before and restores them after, whatever the outcome. The single-threaded executor means no GPS callback can run in between.
  * Rejects names containing `/` or `..` and unreadable files, without touching the map.
  * **Connectivity check** (new code in `navigation_node.cpp`, `navmap.cpp` stays 1:1): the loaded graph is split into connected components; everything outside the largest one can never be reached by route planning. Response: `component_cnt` (1 = connected), `main_node_cnt`/`main_segment_cnt`, `disconnected_way_ids`/`disconnected_node_ids` (OSM ids); `message` becomes `"ok, N component(s) not connected to the main graph"`. Each such component is also logged as `WARN msg="navmap component not connected to the main graph!"` with `node_cnt`, `segment_cnt`, `lat`/`lon` of its first node, `way_ids`, `node_ids`, and `script/navmap_export.sh` prints those lines. A node without any segment cannot occur — `navmap_compress()` has already removed unused nodes, so "isolated" always means a small detached component.
  * The source `.osm` files are kept in `doc/istrobtx_2025/conf/`; copy the one you need into `conf/` first.
  * Call: `script/navmap_export.sh navmap-ba-sadjk` — uses the running `navigation_node`, or starts one from the workspace root just for the export and stops it again (the legacy "compile, run, quit" step). Directly: `ros2 service call /robot/navmap_export istrorsx_core/srv/NavMapExport "{map_name: navmap-ba-sadjk}"`.
  * **Loader rules that decide what ends up in the map** (`navmap_load_osm()`/`navmap_load_osmway()`, unchanged): every `<node>` is loaded first and unused ones are dropped by `navmap_compress()`, so `NAVMAP_NODE_NUM` (60000) must cover *all* nodes in the file, not just the road ones; `NAVMAP_SEGMENT_NUM` (20000) covers segments of accepted ways. Accepted by default: `highway=footway`, `service`, and `track` unless `tracktype=grade3`; `path`/`pedestrian`/`cycleway`/`residential`/`living_street`/scrub/greenfield only under a map-specific `#ifdef ISTRO_MAP_*`. JOSM's `action='delete'` is ignored, but JOSM writes deleted ways without `<nd>`, so they add no segments.
  * The full procedure for adding a new map — OSM cleanup, the per-map sections, the bootstrap placeholders, export and connectivity iteration, compiling the map in, navigation points, QR codes — is `doc/ai/10_new_map_guide.md` (updated from legacy `doc/istrobtx_2025/doc/190317_nova_mapa.txt`).
* **Known gap:** `navigation_point_set()` (called from legacy `process_thread`'s `loadarea_process()` when a QR scan resolves a navigation point's coordinates) has no caller yet — that logic belongs to the not-yet-built `planner_node`, and since `planner_node` would be a *different process*, it can't call `navigation_point_set()` directly the way legacy's single-process app did. `navigation_node` will need a subscriber (QR-scan point index + coordinates) to apply this internally once `planner_node`/`vision_node` exist.

## NN Inference Service — SegFormer-B0 Road Segmentation
* Legacy `istro_rt2025.cpp`'s `vision_thread` talks to a **separate, external Python inference server** over TCP (port `7001`, its own text/binary framing — `VISIONN_HELLO`/`VISIONN_IMPRQ`/`VISIONN_IMPRS`), not to a library linked into the pthread app itself — the C++ side is a thin client (`visionn.h`/`visionn.cpp`, `class VisioNN`, guarded by `system.h`'s `ISTRO_VISIONN`), **built and working, linked directly into `vision_node`** rather than split into its own `istrorsx_nn` package (see Package Overview above — that split is a future idea, not needed for this to work today). The Python server (`doc/istrobtx_2025/visionn_server/`) is architecturally the same kind of thing as `gpsd` is for `gps_node` — an external daemon the ROS side talks to as a client, not itself a ROS node.
* The original `visionn_server.py`/`visionn_model.py` used **TensorFlow 1** (a frozen `model.pb` graph) with a TF-TensorRT acceleration path. This is **not viable on the target Jetson Orin Nano's current JetPack** — NVIDIA has not shipped a TensorFlow/TF-TensorRT package for this JetPack release, only native `tensorrt` Python bindings. Deployment is being redone around a **PyTorch-trained SegFormer-B0 road-segmentation model** (shorthand "segfb0"), exported to ONNX and then compiled to a native TensorRT engine directly (`trtexec`, no TensorFlow involved) — see the separate training repo `~/road-segmentation-20260314-trt` (its `doc/jetson-tensorrt-inference.md` documents the on-device TensorRT build/benchmark path; ~10.3 MB engine, ~18 ms/frame on the Orin GPU).
* Only the **inference-only** files from that training repo belong in `istrorsx_ws` — training code/checkpoints (`train_segformer.py`, `last.pt`/`best.pt`) stay in the separate repo, out of scope here: `infer_image_rosvm.py` (CPU-only reference implementation via ONNX Runtime, verified working on a GPU-less dev VM) plus the exported `segformer_b0_road.onnx` model, and a dedicated venv (`install/setup_cpu_infer_venv.sh` + `requirements-cpu-infer.txt`: `numpy`/`opencv-python-headless`/`onnxruntime`, no PyTorch/CUDA needed for this CPU-only path). The actual on-device TensorRT engine (`.engine` file) is **not portable between machines or TensorRT versions and must be built directly on the Jetson** — it stays out of `istrorsx_ws` the same way the training checkpoints do.
* Now in `istrorsx_ws` at **`script/visionn_segfb0_server/`** (workspace root `script/`, not `src/`) — same category as `script/gpsd_*`: an external, non-ROS Python service, not a colcon package, so it doesn't belong in `src/` until (if ever) it gets rewritten as an actual `rclpy` node. Model file lives in `model_segfb0/segformer_b0_road.onnx` (directory renamed from the training repo's `out_segformer_b0/` — `model_segfb0` names what it *is* here, a deployed model, not a training run's output).
* Two-phase rollout, **both done**: (1) the CPU ONNX Runtime path (`infer_image_rosvm.py` + `model_segfb0/segformer_b0_road.onnx`) runs standalone in `script/visionn_segfb0_server/.venv_rosvm`; (2) `visionn_server.py` wraps it with the **same TCP wire protocol** the legacy `visionn_server.py`/`visionn.cpp` already speak (`VISIONN_HELLO`/`VISIONN_IMPRQ`/`VISIONN_IMPRS`, port `7001`) — kept as close to 1:1 with the legacy file as made sense (identical socket/framing functions `sock_listen`/`sock_recv_skip`/`sock_recv_head`/`sock_recv_img`/`sock_send_hello`/`sock_send_imprs`, identical `process_cmd`/`process_conn` structure, identical `VISIONN_MOCK` debug path), with two deliberate deviations: the log path (see the shared `logout/` bullet below, instead of the legacy's own sibling `../logout/`) and the `VISIONN_MOCK` path (`img_output/testing_mask.png`, matching this directory's own image layout). The not-yet-built `istrorsx_nn` ROS client can be a faithful port of `visionn.cpp` against this server with no protocol changes needed — verified directly with `visionn_test3.py` (see below), a plain-socket client speaking the exact same wire protocol `visionn.cpp` will.
* **Logs to the shared workspace-root `logout/` directory** — the same directory every ROS2 node's log4cxx logging already writes to (see `04_installation.md`). `visionn_server.py` resolves it as `Path(__file__).resolve().parent.parent.parent / "logout"` (file-location-relative, not a hardcoded home directory — this dev VM's `/home/ubuntu` won't match the final Jetson's `/home/istrobotics`); the `.log` filenames themselves (`visionn_server.log`, `visionn_server2.log`) are unchanged from legacy. `visionn_server.log` is the Python `logging`-module file (matches the legacy split); `visionn_server2.log` is the shell-redirected stdout/stderr (`print()` statements, uncaught tracebacks) from `visionn_server_start.sh` — same two-file split legacy already had, just relocated.
* **`visionn_server_start.sh`/`_stop.sh`/`_restart.sh`/`_logtrunc.sh`** (workspace `script/visionn_segfb0_server/`) — ported from the legacy control scripts, all path resolution done relative to the script's own location (`$(dirname "${BASH_SOURCE[0]}")`), never a hardcoded home directory, matching the `visionn_server.py` rationale above. `_start.sh` runs the venv's own interpreter directly (`.venv_rosvm/bin/python3`, no `source activate` needed). `_stop.sh` drops legacy's `sudo` on `pkill -f visionn_server.py` — unnecessary to signal your own background process. `_restart.sh` fixed a real legacy bug found while porting: the original called `./visionn_server_stop.sh`, but the actual legacy file was `visionn_server__stop.sh` (double underscore) — would have failed outright. Standardized on one single-underscore naming convention throughout (matches this project's own `*_run.sh`/`*_node_run.sh` scripts elsewhere), not the legacy directory's inconsistent single-vs-double-underscore split.

### TensorRT Variant — `script/visionn_segfb0-trt_server/`
* A second, sibling server directory for the **actual on-device deployment path**: the CPU/ONNX Runtime server (`script/visionn_segfb0_server/`) exists so the model can be developed/tested on a GPU-less dev VM, but the real target is the native TensorRT engine (see the "PyTorch-trained SegFormer-B0..." bullet above) — this directory is where that engine actually runs. **Unverified on this dev VM** — no TensorRT/CUDA/`cuda-python` here, so nothing in this directory has been executed, only carefully cross-checked line-by-line against `~/road-segmentation-20260314-trt/infer_image_trt.py` (the one TensorRT inference script that *has* been run and benchmarked on the real Jetson, per `doc/jetson-tensorrt-inference.md`).
* Same filenames as the CPU server, same `model_init(log)`/`model_predict(img)` interface, so `visionn_server.py` needed **zero changes** — it's a byte-for-byte copy of `script/visionn_segfb0_server/visionn_server.py`. Only `visionn_model.py` differs internally: `model_init()` deserializes the `.engine` file (`trt.Runtime.deserialize_cuda_engine()`), creates one persistent `IExecutionContext` + device input/output buffers (`cudart.cudaMalloc`/`set_tensor_address`) reused by every `model_predict()` call (never re-allocated per-request); `model_predict()` does the same preprocess → resize-mask-back-to-caller's-size postprocess as the ONNX version, with a CUDA host→device copy / `execute_async_v3()` / device→host copy / stream-sync in between instead of an ONNX Runtime session call. No `close()`/teardown function exists (matches the ONNX version's own design — the process exit is the cleanup, same as legacy never explicitly closing its TF session either).
* **`model_segfb0-trt/segformer_b0_road_fp16.engine`** — copied directly from `~/road-segmentation-20260314-trt/out_segformer_b0/trt/`, flattened (no nested `trt/` subdirectory here, unlike the training repo's own layout). Like the training repo's copy, this file is **not portable** — it must be rebuilt with `trtexec` directly on whichever exact Jetson + JetPack/TensorRT version will run it (see `doc/jetson-tensorrt-inference.md`); it isn't runnable at all here, only carried along as a placeholder/reference until the real deployment happens.
* No `install/` directory or dedicated venv here (unlike `script/visionn_segfb0_server/.venv_rosvm`) — assumes `tensorrt`/`cuda-python`/`cv2` are already present on the target Jetson (JetPack ships `tensorrt` and `cv2` system-wide; `cuda-python` is the one documented manual `pip install cuda-python==13.2.0` step, see `doc/jetson-tensorrt-inference.md`). `visionn_server_start.sh` was adjusted accordingly — plain system `python3`, not a venv-relative interpreter path (the only actual content difference from the copied CPU version's start script; `visionn_server_stop.sh` is an unmodified copy, no venv dependency either way).
* `img_input/` (all 4 sample images, copied from the CPU server dir) and an empty `img_output/` were added so the copied `visionn_test2.py` has something to run against once this is actually deployed — not explicitly requested, but a bare prerequisite for that script to work at all.
* **`visionn_model.py` written**, matching the legacy TF file's exact structure (`mtime_*()` helpers, `model_init(log)`, `model_predict(img)`) but backed by `onnxruntime` instead of a TF session: `model_init()` loads `MODEL_PATH` (module-level constant, `model_segfb0/segformer_b0_road.onnx`) and discovers `input_tensor_name`/`output_tensor_name` from the model itself (`input`/`logits`, mirroring the legacy code's own graph-node-name discovery, not hardcoded); `model_init()`'s first log line includes `path="..."` (the exact `MODEL_PATH` value) so it's always visible in `logout/visionn_server.log` which model file a running server actually loaded; `model_predict()` resizes to the model's fixed `384x512` input (`MODEL_H`/`MODEL_W` constants), runs inference, `argmax`s the 2-channel logits into a 0/255 mask, and **resizes the mask back up to the caller's original image size** before returning — this is a deliberate difference from the legacy TF model (which happened to already match the camera's native 640x480 resolution, so needed no resize either way) that keeps `model_predict(img)`'s contract identical for any caller regardless of the model's fixed internal input shape. `visionn_test.py` and `visionn_test2.py` (from the legacy `visionn_test5_trt.py` — renamed twice: "trt" dropped since this path is plain ONNX Runtime not a TensorRT engine, then `test5`→`test2` per user request; its log file is `visionn_test2.log`, matching the script name) mirror the legacy test scripts' structure 1:1.
* All sample/test images and every script-generated result live under two fixed subdirectories, never loose in `script/visionn_segfb0_server/` itself: **`img_input/`** (every sample `.png` — the 3 originally under `test/image/` plus `testing_image.png`, consolidated into one place) and **`img_output/`** (every script-generated result — `infer_image_rosvm.py`'s `*_overlay.png` files, `visionn_test2.py`'s `testing_mask.png`, `visionn_test3.py`'s `visionn_test3_mask.png`). `infer_image_rosvm.py`'s `IMG_PATH`/`OUT_DIR`, `visionn_test.py`/`visionn_test2.py`'s hardcoded `img_input/testing_image.png`/`img_output/testing_mask.png` paths, `visionn_server.py`'s `VISIONN_MOCK` path, and `visionn_test3.py`'s input/output paths all point here — no script writes or reads a bare filename in the working directory anymore.
* **`visionn_test3.py`** is not a model test like the others — it's an **end-to-end TCP protocol test client** for `visionn_server.py`, speaking the raw `VISIONN_HELLO`/`VISIONN_IMPRQ`/`VISIONN_IMPRS` wire protocol over a real socket exactly like the legacy C++ `visionn.cpp` client would, rather than calling `visionn_model.py` in-process. Verified end-to-end against a running `visionn_server.py`: HELLO round-trips correctly, an `IMPRQ` request with `img_input/testing_image.png` gets back a correctly-decoded mask (`480x640` uint8, values `{0, 255}`), and the server's own log shows the expected `sock_recv_img()`/`model_predict()`/`sock_send_imprs()` timing sequence. (The `ConnectionResetError` logged right after — from the test client closing its socket without another command — is expected/benign, matching how the legacy server's own `process_conn()` try/except handles any client disconnect, not a bug.)

### Second Model Family — YOLO11s-seg Road Segmentation, `script/visionn_roadyolo-trt_server/`
* A **third sibling server directory**, alongside `segfb0`/`segfb0-trt` above, for a different-model-family alternative to SegFormer-B0: a YOLO11s-seg TensorRT engine, single class `road`, trained/exported in a separate reference project `~/pablo_trenovanie_NN-mix/road-seg-yolo-20260826-win/` (`infer_trt.py` + `roadseg_post.py`, itself modeled on `~/road-segmentation-20260314-trt`'s own `infer_image_trt.py`). Selected via `visionn_server_variant:=roadyolo-trt`; the launch-time default stays `segfb0` — this is an additional opt-in choice, not a replacement.
* Same `visionn_server.py`/`visionn_server_stop.sh` (byte-for-byte copies of `segfb0-trt`'s), same `model_init(log)`/`model_predict(img)` interface. Only `visionn_model.py` differs, and differs more than the CPU→TRT SegFormer swap did, because the underlying model shape is genuinely different:
  * **Two engine outputs, not one** — a 3-D detections tensor `(1, 4+nc+32, N)` (box + 1 class score + 32 mask coefficients per candidate) and a 4-D prototypes tensor `(1, 32, mh, mw)`. Tensor names are **discovered generically** (`engine.num_io_tensors`/`get_tensor_name`/`get_tensor_mode`, the two outputs told apart by `len(shape)`) rather than hardcoded like `segfb0-trt`'s `"input"`/`"logits"` — a deliberate deviation, since this engine's output order/names are not guaranteed the way SegFormer's fixed two-name ONNX export was. Ported from `infer_trt.py`'s `TrtSegmenter.__init__`.
  * **Real detection postprocess, not a plain argmax** — confidence threshold (0.10, the same value the reference project's own validation tuning settled on) → greedy NMS (IoU 0.7) → `coeffs @ protos` mask-coefficient/prototype matmul → crop letterbox padding **at prototype resolution**, then one resize straight to the caller's image size (this order is load-bearing, verified bit-identical to `ultralytics` in the reference project — do not reorder) → per-instance box crop → OR-combine into one binary mask. Ported near-verbatim from `roadseg_post.py` (Slovak comments translated to English), inlined directly into `visionn_model.py` rather than split into a sibling module the way the reference project splits it — that split exists there only to share one postprocess between an ONNX and a TensorRT runtime; this repo has only one runtime per variant, so a split would buy nothing and would break the "one self-contained `visionn_model.py` per variant" convention every other variant already follows.
  * `MODEL_H`/`MODEL_W` are **not** hardcoded module constants (unlike `segfb0-trt`'s `384`/`512`) — they're read back from the engine's own discovered input shape in `model_init()`, so they can't silently drift from whichever `.engine` file `MODEL_PATH` points at. Fixed 480×640 (H,W), `dynamic=False` at export — no `context.set_input_shape()` call needed.
  * `infer_trt.py`'s own multi-backend `CudaBuffers` abstraction (auto-detecting cuda-python/PyTorch/pycuda) was **not** ported — unnecessary generality here, since the target is always the same one Jetson with the same one proven CUDA backend `segfb0-trt` already uses (`cuda.bindings.runtime`), and `overlay_mask()`/`TrtSegmenter`/the CLI driver are visualization/standalone-script concerns the server doesn't need.
* **`model_roadyolo-trt/road_yolo11s_seg_fp16.engine`** — copied directly from the reference project (23MB). Same non-portability caveat as `segfb0-trt`'s engine: built via `trtexec` (`build_engine_jetson.sh` in the reference project) directly on this exact Jetson + JetPack/TensorRT version, cannot be copied from a different machine/TensorRT version.
* **Verified dependency finding (2026-09-12)**: plain system `python3` on this Jetson does **not** have `cuda-python` importable (`ModuleNotFoundError: No module named 'cuda'`) — checked directly, contrary to what might be assumed from `segfb0-trt`'s own doc bullet above ("assumes `tensorrt`/`cuda-python`/`cv2` are already present on the target Jetson"). The one place `cuda-python` actually is installed is inside a *different* sibling project's venv, `~/pablo_trenovanie_NN-mix/road-segmentation-20260314/.venv_trt` — which `segfb0-trt`'s own `visionn_server_start.sh` already prefers (falling back to plain `python3` only if that venv is absent). `roadyolo-trt`'s `visionn_server_start.sh` is an unmodified copy of `segfb0-trt`'s (same venv-preference logic, comment expanded to explain it's currently load-bearing here, not just a dev-machine fallback) — if `.venv_trt` is ever removed/moved, both TensorRT variants need `cuda-python` installed against whatever replaces it before either can start.

### CPU/ONNX Variant of the Same Model — `script/visionn_roadyolo_server/`
* The YOLO11s-seg model as **plain ONNX Runtime on the CPU**, so different networks can be compared on a GPU-less VM (cloud or dev box) over the same wire protocol and the same inputs. `roadyolo-trt` is the Jetson deployment of this same model; `segfb0` is the CPU server of the other model family. Selected via `visionn_server_variant:=roadyolo` — the launch discovers it from the directory name, no launch-file edit was needed.
* **Shares the venv with `segfb0`**: `visionn_server_start.sh` prefers `../visionn_segfb0_server/.venv_rosvm/bin/python3` and falls back to plain `python3`. Both are CPU/ONNX servers needing the same three packages, so a second venv would only be another copy to keep in step — the same reasoning by which the two TensorRT variants share `.venv_trt`. On a fresh VM: `../visionn_segfb0_server/install/setup_cpu_infer_venv.sh`.
* **`visionn_server.py` is a byte-for-byte copy of `segfb0`'s**, not of the TensorRT variants' — it is the one that carries the `VISIONN_MIN_PERIOD` inference throttle, which CPU inference needs (default 1000 ms here; set `VISIONN_MIN_PERIOD=0` for an unthrottled model comparison).
* **`visionn_model.py`**: the whole pre/postprocess block (`letterbox`, `preprocess`, `nms`, `postprocess`) is **identical to `roadyolo-trt`'s**, verified by AST comparison, so the two runtimes of this model cannot drift apart. Only the runtime differs — an `ort.InferenceSession` instead of engine/context/CUDA buffers. Input size and the two output names are read back from the model itself, the outputs told apart by rank (`len(shape)`), same as the engine variant.
* **`model_roadyolo/road_yolo11s_seg.onnx`** (40 MB) — the export the Jetson engine was built from, `archive/260826_road-seg-yolo-win/runs/road/weights/best.onnx`. Unlike an `.engine`, an ONNX file is portable, so this one runs anywhere.
* **Measured on this dev VM** (4 sample images, unthrottled): ~250-340 ms per `model_predict()`, masks agreeing with `segfb0`'s at IoU 0.987-1.000. `model_init()` reports the same tensor shapes the Jetson logs for its engine — `[480, 640]`, `(1, 37, 6300)`, `(1, 32, 120, 160)`.

Symmetrically, `planner_node` will also compute `lidar_dmap` itself from `lidar_node`'s already-published raw `LidarData.msg`, via `Lidar::process()` (already-ported legacy code, cheap CPU-only geometry — legacy computes it synchronously inside `process_thread`, not in a separate thread, unlike vision's dmap which needs a NN round-trip and so runs in its own thread/node). **`lidar_node` needs no changes for this.**

A message, not a service — matches every other cross-node control interaction in this project (`DriveCommand`, `NavigationData`), deliberately not introducing services as a new pattern.
* **`VisionData.msg` + `VisionDebugData.msg`** (written) — the "one message vs. a lighter/heavier pair" question from the original design is resolved as **two messages**, following the same split already established between `ServoData`/`ImuData` (two concerns from one tick, two topics) rather than `CameraFrame.msg`'s "no composition" precedent (which was for two halves of one inseparable capture, a different situation):
  * **`VisionData.msg`** — driving-relevant only: `camera_id` (0=front/1=rear, matching `camera_node`'s own `conf.cameraDeviceId` semantics — added after review, so a message is self-describing even out of topic context, e.g. in a bag replay), the `DegreeMap` (`dmap`/`dist`/`maxd`, fixed `int32[181]`, 181 = `DEGREE_MAP_COUNT`), `angle_min`/`angle_max`, and `qrscan_latitude`/`qrscan_longitude` (only ever set on the front-camera topic — legacy never QR-scans the rear camera). One type, published on two topics (`/robot/vision_front_data`/`/robot/vision_rear_data`), same reuse pattern as `CameraFrame.msg` across the two `camera_node` instances.
  * **`VisionDebugData.msg`** — everything `save_node` needs for `Vision::drawOutput()`'s "vision" overlay image plus the raw NN prediction mask, kept **out** of `VisionData.msg` so `planner_node` never has to receive it: `markers`/`epweight`/`elweight`/`camera_img_pred`, each as a `width`/`height`/`cv_type`/`step`/`data` group (same flat, no-composition `cv::Mat`-serialization convention as `CameraFrame.msg`), plus `camera_id` and a duplicated `angle_min`/`angle_max` (so `save_node` can call `drawOutput()` from this one message alone, without correlating two topics/timestamps for one saved image). **`vision_markersIM` is deliberately excluded** — checked `Vision::drawOutput()`'s actual signature and every `save_thread` call site: `markersIM` is only ever consumed internally by `Vision::eval()`, nothing downstream needs it. `vision_node` publishes this and `save_node` alone decides whether/how often to actually write it to disk (rate-limited by disk/OS load in legacy `save_thread`) — `vision_node` does not gatekeep.
* **New calibration assets, both now in place**: `sample/` (workspace root, 62 JPEGs with hardcoded per-file pixel coordinates in `loadSampleOnRoad()`/`loadSampleOffRoad()`, required for `Vision::init()`'s `calcKMeans()` — runs unconditionally, even in the NN-active build) and `conf/vision_mask.png` (+ `_black`/`_white` variants, `loadEPMask()`) — both copied from `doc/istrobtx_2025/`, same relative-to-workspace-root convention as `conf/`/`logout/`/`out/` already established elsewhere.
* **New system dependency**: `libzbar-dev`/`libzbar0` (ZBar, `QRScanner`'s `#include <zbar.h>`) — install command already known (`sudo apt-get install libzbar-dev libzbar0`, from `doc/istrobtx_2025/script/install/zbar_install.sh`), not yet ported into this workspace's `script/install/`.

## `planner_node` (Design Analysis, `istrorsx_core`) — Fusion/Decision Node
**Built 2026-08-27 — code-complete, builds clean, smoke-tested; not yet functionally exercised.** This section originally recorded a source-level analysis of legacy `process_thread` (`istro_rt2025.cpp`) and its seven collaborator functions, done before any code was written — same "analyze and document first" sequencing as `vision_node`'s own design phase. All open design questions were decided (see below) and then implemented: `PlannerData.msg`/`NavigationPointSet.msg`/`GetWMGridSnapshot.srv`, `lidar_process()` (extracted into `istrobtx`), `wmodel.h`/`.cpp` (copied verbatim into `istrorsx_core`), `istro_main_planner.cpp`/`.h`, and finally `planner_node.hpp`/`.cpp` itself — `process_thread` and all 7 collaborator functions ported as private `PlannerNode` methods, following the user's explicit "1:1 where reasonable" direction (struct-field-access code bodies are near-verbatim copies of the legacy functions; only the enclosing signature changed from a free function to a method). `DataSet` (`istrobtx`) was extended with `vision_dmap`/`vision2_dmap`/`lidar_dmap` (+ their angle_min/max/stop fields) and `qrscan_latitude`/`longitude`, finally closing the `lidar_dmap` gap flagged since `lidar_node` was built. `CMakeLists.txt` wired a new `planner_node` executable (source list includes `navig.cpp`/`navmap.cpp`/etc. purely for `wmodel.cpp`'s `drawGridFull()` link-time symbols, never called by `planner_node` itself). Build: zero warnings, zero errors. Smoke test (`ros2 run` + `SIGTERM`): clean startup, correct idle behavior (silent until real sensor messages arrive, matching `plannerTick()`'s own "did new data change" gate), clean shutdown. **Not yet done**: an actual `plannerTick()` decision cycle exercised with real/simulated messages — full details in `03_progress.md`'s "`planner_node.hpp`/`.cpp` Written & Built" milestone.

**Known build-wiring implication, not yet acted on**: `wmodel.cpp`'s `drawGridFull()` (never called by `planner_node`, exclusive to the future `save_node`, see decision #4) still references `navigation_point_cnt()`/`navigationPointXY[]`/`navigationPoint[]` from `navig.cpp`/`navig_data.cpp` — since `wmodel.cpp` is one translation unit, those symbols must resolve at **link** time even though `planner_node`'s own code never calls that function. This means `planner_node`'s `CMakeLists.txt` executable will need `navig.cpp`/`navig_data.cpp`/`navmap.cpp`/`navmap_data.cpp` linked in too (plus, transitively, `libxml2`), purely to satisfy `wmodel.o`'s unused-by-`planner_node` code path — not needed for the standalone smoke-compile done so far (which only compiles, doesn't link), but will surface as an undefined-reference link error once `planner_node`'s executable target is added. Flagging now so it isn't a surprise later.

**Port scope**: `process_thread` itself, plus (all in `istro_rt2025.cpp`, not separate files — legacy keeps them as free functions/structs directly above `process_thread`): `update_angle_interval()`/`update_speed_interval()` (small angle/speed-interval-tracking helpers), `calib_process()` (+ `calib_t` struct, two instances — see below), `wrongway_process()`/`wrongway_check()`/`wrongway_force()` (+ `wrongway_t`), `detectobst_process()` (+ `detectobst_t`), `loadarea_process()` (+ `loadarea_t`), `update_xy()` (odometry integration), `speedctl_process()` (+ `speedctl_t`), and `process_readData()`/`process_writeData()`. This **is** the one node with no existing legacy `.h`/`.cpp` module of its own — everything above lives inline in `istro_rt2025.cpp`.

**`wmodel` (`WorldModel`/`WMGrid`, `wmodel.h`/`.cpp`) is shared between `planner_node` and the future `save_node`, not owned by `planner_node` alone — see decision #4 below.** In legacy this is a single global object both `process_thread` and `save_thread` reach directly (same process, shared memory — `save_thread`'s own source even flags this access `// fixme: not thread safe!`); `WMGrid::drawGrid()`/`drawGridFull()` are the slow, disk/CPU-heavy rendering calls, and legacy deliberately keeps them **exclusive to `save_thread`** so they never block `process_thread`'s real-time 20ms decision loop — `process_thread` only ever calls the cheap `updateGrid()`/`evalGrid()`. That division must be preserved 1:1: `planner_node` never calls `drawGrid()`/`drawGridFull()` either. `wmodel.h`/`.cpp` copies verbatim into `istrorsx_core/include/istrorsx_core/istrobtx`/`istrorsx_core/src/istrobtx` (**not** the shared cross-package `istrobtx` package) — same "same-package, no cross-package boundary" reasoning already used for `navig.h`/`navmap.h` (`01_architecture.md`, `navigation_node` section), and necessary here for a real reason: `WMGrid::drawGridFull()` itself calls `navigation_point_cnt()`/reads `navigationPointXY[]`/`navigationPoint[]` (to overlay nav-point labels on the debug image) — a genuine dependency on `istrorsx_core`'s own `navig.h`/`navig_data.h`, which rules out the shared `istrobtx` package the same way it would for any other `istrorsx_core`-only header.

**Inputs (all cross-process, no `DataSet`-shared-memory shortcut left)**:
* `NavigationData.msg` (`navigation_node`) — `navp_*`/`ref`/`x`/`y`, replaces `process_readData()`'s `gps_navp_*`/`gps_ref`/`gps_x`/`gps_y` fields.
* `VisionData.msg`/`VisionDebugData.msg` ×2 (`vision_node`, front+rear topics) — replaces the `THDATA_STATE_VISION_PROCESSED`/`VISION2_PROCESSED` polling branches.
* `LidarData.msg` (`lidar_node`) — replaces the `THDATA_STATE_LIDAR_CAPTURED` polling branch; `planner_node` calls `Lidar::process()` on the raw scan itself (see open question below), matching legacy computing `lidar_dmap` synchronously inside `process_thread`, not in a separate thread.
* `ServoData.msg` (`ctrlboard_node`) — `ircv500`/`angle`/`velocity`/`loadd`/`time1` (already consumed by `drive_node`; `planner_node` needs its own independent subscription, a second/different consumer of the same topic).
* `ImuData.msg` (`ctrlboard_node`) — **new input, not currently consumed by any `istrorsx_core` node.** `euler_x` is `process_readData()`'s `ctrlb_euler_x`, the only currently-*active* yaw source besides raw odometry (see "yaw calculation" below).
* `GpsData.msg` (`gps_node`) — `speed`/`course`, needed directly by `calib_process()` (`gps_course`/`gps_speed` parameters); `navigation_node` doesn't re-publish these itself since it's a route/position layer, not a raw-fix passthrough, so `planner_node` subscribes to `gps_node` in parallel with `navigation_node`, same as it does with `ServoData`/`ctrlboard_node`.

**Confirmed NOT needed** (dead code in legacy, not ported, matching the project's existing convention of dropping genuinely-unreachable branches while still preserving `#ifdef`-gated compile-time variants): the `ahrs_yaw`/`gps_lastp_azimuth` yaw-fallback block (lines ~3104-3113) is entirely commented out in `istro_rt2025.cpp` itself — `ahrs_thread`/a separate AHRS device was already effectively retired before this port even started (`dataset.h`'s `ISTRO_ROS2` branch already dropped `ahrs_roll`/`pitch`/`yaw` entirely, keeping them only in the legacy-only `#else`). No `GpsData.msg` changes needed for this.

**Yaw calculation** (`process_thread`'s "calculate yaw" block): two live sources, `yaw_src=0` = `process_yaw` (last value `update_xy()` computed, i.e. odometry-integrated heading) and `yaw_src=1` = `ctrlb_euler_x` (compass, overwrites the odometry value whenever a fresh `ImuData` arrives) — both ported as-is. `nav_angle` (steering error vs. the navigation goal) then has its own two-source fallback: `"YAW"` (using `conf.navigationImuYaw`, a fixed-heading mode) or `"AZIMUTH_YAW"` (using `navp_azimuth` from `navigation_node`) — both `#if`-free, always-compiled, ported verbatim.

**Compile-time variants already active in `system.h`, all to be ported (not just the active branch — same "port every variant" precedent as `navmap_data.cpp`)**: `ISTRO_CAMERA_REAR` (rear-camera dmap→wmodel + `vision_stop_bck` obstacle-behind-check, active), `ISTRO_CALIB2` (a second, parallel `calib_process()` instance — its own comment says "iba na priebezne kontrolovanie... nepouziva sa pre navigaciu", i.e. logging/monitoring only, its result never feeds `process_angle`/`process_state`; active), `ISTRO_VISION_ORANGECONE` (Roboorienteering cone-seeking alternative to normal wmodel-based driving — currently inactive/`#else` branch compiled, but the `#ifdef` branch ports too), `ISTRO_WRONGWAY_DISABLE` (currently inactive). All four flags/fields already exist in the shared `istrobtx` `system.h`/`config.h` — no gap there.

**Tick structure — resolves the "how many tick functions" question also raised during `vision_node`'s design** (this time it's not 2, but 4 separate entry points, since `process_thread` polls 3 independent "fast" data sources plus runs its own 20ms decision timer):
1. `cb_vision_front()` / `cb_vision_rear()` (if `ISTRO_CAMERA_REAR`) — on `VisionData` arrival, immediately folds the dmap into `wmodel.updateGrid()` (or, under `ISTRO_VISION_ORANGECONE`, computes `coneseek_angle_min/max/intlen` via `DegreeMap::findbnd()` instead — no `wmodel` write in that mode). Matches legacy's non-blocking `checkData(THDATA_STATE_VISION_PROCESSED, ...)` poll, now event-driven.
2. `cb_lidar()` — on `LidarData` arrival, calls `Lidar::process()` (see open question below) then folds into `wmodel.updateGrid()`. Matches the `THDATA_STATE_LIDAR_CAPTURED` poll.
3. `plannerTick()` — a 20ms `rclcpp::WallTimer`, mirroring `drive_node`'s own `controlTick()` precedent, replacing legacy's `timeDelta(process_to) >= PROCESS_PERIOD_MIN` poll-and-compare-timestamps gate. Reads the latest cached `ServoData`/`ImuData`/`GpsData`/`NavigationData` member state (updated by their own lightweight subscription callbacks, no per-field "did this change" tracking needed the way legacy's `last_gps_time`/`last_ctrlb_time1`/`last_ctrlb_time2` comparison did — a ROS timer firing IS the "do_process" signal), then runs the full decision chain: yaw/`nav_angle` → `wmodel.evalGrid()` → `loadarea_process()` → `detectobst_process()` → `calib_process()`(×2) → `wrongway_process()` → angle/state resolution (`CALIBRATION`/`CONE_SEEK`/`NAV_ANGLE`/`MIN_MAX`) → `speedctl_process()` → `update_xy()` → publish.

No separate callback is needed for `VisionControl.msg` — `planner_node` *publishes* it (ports `vision_thread_qrscan_enable/disable()`/`processRear_enable/disable()`, called from `loadarea_process()`/`wrongway_process()` today), it doesn't subscribe to it; that's just another `publishXxx()` call made from inside `plannerTick()`/the fast-path callbacks above, same pattern as every other cross-node control message in this project.

**Outputs**:
* `DriveCommand.msg` (already exists, unchanged) — `angle`/`velocity`/`state`/`stop`/`yaw`, published every `plannerTick()`, consumed by `drive_node`.
* `VisionControl.msg` (already exists, unchanged) — `qrscan_enabled`/`process_rear_enabled`, published from `loadarea_process()`/`wrongway_process()` call sites.
* `PlannerData.msg` (new, see decision #3 below) — `image_number`, `process_dir`, `process_ref`, `process_x`, `process_y`, `process_backward`, `coneseek_stop`, `coneseek_intlen`.
* `NavigationPointSet.msg` (new, see decision #3 below) — closes the `navigation_point_set()` cross-process gap, subscribed by `navigation_node`.
* `GetWMGridSnapshot.srv` (new, see decision #4 below) — a **service**, not a topic: `planner_node` hosts it, `save_node` calls it only when it decides to render+save, matching legacy's pull-based `save_thread` semantics. `planner_node` never calls `drawGrid()`/`drawGridFull()` itself.
* **Not an output at all, forward-looking note for the future `save_node`**: `saveNavMap()`'s `navmap_export_kml()`/`navmap_draw()` (also legacy `save_thread`) need `navMapNode[]`/`navMapSegment[]`, but that data is `navigation_node`'s **compile-time-constant** route graph (`navmap_data.cpp`), not live state — so `save_node` doesn't need anything from `planner_node`/`navigation_node` for this at all, it just links `navmap.h`/`navmap.cpp`/`navmap_data.cpp` directly (same-package, no cross-process boundary, same reasoning `navig.h`/`navmap.h` already use) and calls `navmap_draw()`/`navmap_export_kml()` itself. The small `auxpt`/GPS-breadcrumb-trail (`gps_pt[]`) inputs those calls also need are likewise not a new mechanism — `save_node` derives its own copy from `GpsData.msg`/`NavigationData.msg`, both already-published regular messages. See `05_migration_guide.md` § "Cross-Node Access to Complex/Large Internal State" for the full reasoning (this is where the general messages-vs-services-vs-direct-linking rule came from).
  * **Corrected 2026-09-06**: this was right about the *topology* (`navMapNode[]`/`navMapSegment[]`'s positions/connectivity) but wrong to lump `NAVMAP_FLAG_ROUTE` in with it — that flag is live, mutable, per-process state, set by `navmap_planRouteLL()`/cleared by `navmap_plan_delete()`, both called only from `navigation_node`'s own process. `save_node`'s separately-linked copy never had it set, so `navmap_draw()`'s green route highlighting and `navmap_export_kml()`'s `lstyle2` route styling were silently always empty — found via the user visually inspecting a `test_gps_gen.sh`-generated `navmap.png`. Fixed with `NavigationRoute.msg` (`navigation_node` → `save_node`, published every `navigationTick()`, same cadence as `NavigationData.msg`), which carries **everything `navmap_planRouteLL()` changes about the graph**: the `NAVMAP_FLAG_ROUTE`- and `NAVMAP_FLAG_INVISIBLE`-flagged base-segment indices, plus the temporary nodes and segments it splices in via `navmap_node_add()`/`navmap_segment_add()` (`NavMapNode.msg`/`NavMapSegment.msg`, at most 3 and 6 per plan). `save_node`'s `cb_navigation_route()` replays that with the same primitives — `navmap_plan_delete()`, then re-add the temporaries in published order, then apply the flags — so `navmap_draw()`/`navmap_export_kml()` need no changes at all: they already read these flags off the same shared globals. The temporaries are appended at the tail of both arrays and dropped again by `navmap_plan_delete()`, which is what keeps base indices identical in both processes; `base_node_count` in the message is checked against the receiver's own count and the plan is rejected if they differ, since the temporary segments' node indices would then not line up. `NAVMAP_FLAG_ROUTE_OPDIR` is deliberately not carried — `navmap` uses it for route following only, never for drawing or KML export.

### Threading — the one node that is not single-threaded

`planner_node` runs a `MultiThreadedExecutor` with **2 threads** and two `MutuallyExclusive`
callback groups. Every other node in this project uses plain `rclcpp::spin()`.

* **The split**: `cb_servo`/`cb_imu`/`cb_gps`/`cb_navigation` in their own group; the 5 ms timer,
  `cb_vision_front`/`cb_vision_rear`, `cb_lidar`, `cb_config` and the `GetWMGridSnapshot` service
  in the default group, mutually exclusive exactly as before. Two threads is the maximum that can
  ever be busy — two exclusive groups cannot run three callbacks at once.
* **Why those four**: they are what gates `plannerTick()`'s processing (a tick does nothing until
  `ctrlb_time1`/`ctrlb_time2`/`gps_time` changes), so they must not queue behind it.
* **Why it needs no locking**: each of the four writes *only* into the legacy `DataSet` through
  `threads.getData(THDATA_STATE_SHARED, THDATA_STATE_SHARED_LOCK)` / `setData()`, which is a real
  mutual-exclusion handoff left over from the threaded monolith, and none of them reads or writes
  a single `PlannerNode` member. **Nothing else may be moved into that group without checking the
  same two things** — `cb_vision_*`/`cb_lidar` share nine plain members with the timer
  (`coneseek_stop_`, `qrscan_latitude_`/`_longitude_`, `vision_lastt_`, `vision_stop_bck_`/`_cnt_`,
  `lidar_angle_min_`/`_max_`, `lidar_stop_`) and `cb_config` writes `conf.velocityFwd*` unprotected.
* **Groups are not pinned to threads.** `MutuallyExclusive` guarantees only that two members of one
  group never run *simultaneously*; any callback may run on either thread from one call to the next.
  `plannerTick` and `cb_servo` are both seen on both threads — their overlap is the whole point.
* **Reading it in a log**: `LOG_THREAD_NAME_ONCE("exec2")` (`logger.h`) names the second thread the
  first time a sensor callback lands on it. `threadName` is thread-local MDC that `main()` sets only
  for its own thread, and the macro never overwrites an existing name. Grep for `[exec2]` to see
  whether the second thread was needed at all; under light load one thread drains everything.
* **Known sharp edge**: `Threads::getData()` busy-waits with `msleep(2)` when the slot is held. It
  was never contended before this change.

### `WRONG_WAY` — two different triggers, one state machine

Worth spelling out because the name suggests only the first of the two, and the second is what
actually fires most often. Both live in `planner_node.cpp` and both end in
`PROCESS_STATE_WRONGWAY`, driven by the same `wrongwayProcess()` phase machine.

**Trigger A — `wrongwayCheck()`: "I am heading away from where I am going."** The literal reading of
the name. Requires a navigation goal and a heading to compare against:
* `angle` (target direction minus own heading) outside `WRONGWAY_ANGLE_MIN/MAX` = **±60°**. Inside
  that band the check is cancelled outright ("angle is OK").
* distance to the next navigation point above `CALIB_NAVP_DIST1` — cancels if the point is already
  close, so approaching a waypoint is never mistaken for driving away from it.
* the target direction must stay stable while the check runs: `yaw0` spread above
  `WRONGWAY_YAW0_DIFF` = **45°** cancels it (the goal moved, so the disagreement was not ours).
* while `ctrlb_ircv500` (encoder speed) is under `WRONGWAY_IRCV500_MIN_VALUE`, standing still is
  accumulated separately rather than counted as driving the wrong way.

**Trigger B — `wrongwayForce()`: "there is nowhere to go."** Nothing to do with the map. Fires when
vision reports no drivable direction (`process_angle >= ANGLE_OK`, i.e. no angle) continuously for
`PROCESS_NOANGLE_TO` = **1200 ms**, logged as `process_angle("WRONG_WAY_FORCE")`. This is the one
that dominates whenever the robot faces a wall or a dead end — the planner's way of saying "back out
and turn round", not "I misread the map".

**The phase machine** (`wrongwayProcess()`), same for both triggers, timed from the trigger instant:

| until | phase | commands |
|---|---|---|
| `WRONGWAY_TIME1_STOP` 3000 ms | STOP1 | `angle=90` (straight), `velocity=VEL_ZERO` |
| `WRONGWAY_TIME2_BACK` 3250 ms | BACK2 | `angle=90-angle` (clamped to the navigation limits), `velocity=VEL_ZERO+conf.velocityBack` |
| `WRONGWAY_TIME3_STOP` 3500 ms | STOP3 | straight, stop |
| `WRONGWAY_TIME4_BACK` 6000 ms | BACK4 | reverse again |
| `WRONGWAY_TIME5_STOP` 9000 ms | STOP5 | straight, stop |

So a full cycle is stop → reverse → stop → reverse → stop over nine seconds, and it repeats while
the trigger condition holds. `ISTRO_WRONGWAY_DISABLE` (`system.h`, currently inactive) compiles the
whole thing out.

**Reading it in a log**: `process_angle("WRONG_WAY_FORCE")` carries `noangle_dt`, the time vision has
had nothing drivable — compare it against 1200 ms to see it cross the threshold. `wrongwayCheck()`'s
own path instead logs `"wrongway-check start!"` and its cancellations
(`"wrongway-check interrupted (angle is OK)!"`, `(navp_ok is FALSE)`, `(yaw0_diff exceeded)`), so
which of the two fired is unambiguous from the log alone.

**Held while waiting or in emergency** (`PlannerNode::wrongwayHold()`, a deliberate deviation from legacy,
whose `process_thread` had neither rule). Neither trigger may start, nor a running cycle continue, while
the robot is not supposed to drive:
* **Hold sources**, checked each tick right after `loadareaProcess()`:
  * `"loadarea"` — a wait set `process_angle_` (LOADING, UNLOADING, QRSCAN_COORD, BALLDROP). Legacy
    already blocked new triggers here, but not a cycle that was already running.
  * `"emergency"` — `ServoData.state == CTRLB_STATE_EBTN` (big red button). Legacy ignored it entirely:
    the standing robot saw a person in front, got `NO_ANGLE` and forced WrongWay every ~10 s for as
    long as the button was held (29 of 77 cycles in the 2026-09 field logs). `drive_node` sent no speed
    meanwhile, but the cycle kept running and could resume mid-reverse on release.
* **While held**: `noangle_to_` and the check timer are reset every tick, and a running cycle is
  **cancelled** (back to `wrongwayInit()`, rear vision off) — not paused, so releasing the button never
  continues a reverse.
* **Grace period `WRONGWAY_HOLD_GRACE` = 3000 ms after the hold ends**: `wrongwayCheck()` is skipped and
  `noangle_to_` keeps being reset, so the earliest force is ~4.2 s after a wait or an emergency ends.
  This is what covers the QR case: the wait ends the moment coordinates arrive, while the person with
  the phone is still in front of the robot — before, the force fired 1.2 s later.
* **Log**: `wrongwayHold(): msg="wrongway hold start!", reason=…` and `msg="wrongway hold end!", reason=…,
  hold_dt=…` on transitions only, and `msg="wrongway cancelled!", reason=…, wrongway_dt=…` when a
  running cycle is dropped. `script/log/wrongway_analyze.py` reports such cycles as
  `skipped reason="cancelled_<reason>"`.
* **Not covered — MANUAL mode**: the planner does not know `drive_node`'s steering type, so WrongWay
  still runs in MANUAL (ignored by `drive_node`), and switching to AUTONOMOUS mid-cycle can reverse at once.

**When a reversal is not supposed to move the robot** — all of these are correct behaviour, not failures:
* **emergency** — board `state=8` (`CTRLB_STATE_EBTN`); the board itself holds the motor.
* **MANUAL** — `drive_node` ignores planner velocity outside `AUTONOMOUS` (display text `DM…` instead of `DA…`).
* **`process_stop`** — while reversing, `planner_node` sets `process_stop = vision_stop_bck_`: the rear camera
  sees no free path behind (`DETECTOBST_BCK_ANGLE_MIN/MAX` 60/120°, `DETECTOBST_BCK_COUNT` 3 frames).
  `drive_node` then sends `VEL_ZERO`. In grass this can deadlock — no way forward, no way back — and the
  cycle repeats every ~10 s without motion.
* **board obstacle** — board `state=6/7` (`OBSTB`/`OBSTA`, rear ultrasonic); `ctrlb_obstState()` blocks the command.

**Backward check** (`DriveNode::wrongwayBackCheck()`, diagnostic only, changes no behaviour). Tracks every
stretch where all conditions for reversing hold at once — `AUTONOMOUS`, `PROCESS_STATE_WRONGWAY`,
`process_velocity_last_ < VEL_ZERO`, `process_stop <= 0`, no `EBTN`, no board obstacle — and judges it when it ends:
* shorter than `WRONGWAY_BACKCHECK_MIN_TIME` (1500 ms) — not judged, so the 250 ms BACK2 pulse never reports.
* board never reported `ctrlb_velocity < VEL_ZERO` → `WARN msg="wrongway backward FAILED!", reason="board_ignored"`.
* board took it, but `ircv500` (encoder pulses over 500 ms) never reached `WRONGWAY_BACKCHECK_IRCV500` (5.0, the
  planner's own "standing still" threshold) → `WARN … reason="no_wheel_motion"`.
* `ServoData` older than 500 ms during the stretch → `WARN … reason="no_telemetry"`.
* otherwise `INFO msg="wrongway backward OK"`.
* fields: `back_dt`, `velocity`, `ctrlb_state`, `ctrlb_velocity` (last seen while reversing), `ircv500_max`, and
  `end` — what ended the stretch (`phase_end`, `process_stop`, `emergency`, `manual`, `board_obstacle`, `wrongway_end`).

`ctrlb_velocity` in `ServoData` is the board's current motor setpoint, so it separates "the command never took"
from "the command took but nothing turned". Only the latter points at the motor controller or mechanics.

**Offline**: `script/log/wrongway_analyze.py LOGDIR…` reconstructs the same verdict from the raw DEBUG
telemetry of any run, including logs older than the check itself. It judges the BACK4 phase of every
`"wrongway start!"`, prints one log-format line per cycle (`WARN` for failures, `-f` failures only, `-v` adds
the board timeline) and a per-run summary. Its skip reasons match the list above.

### Compass calibration — `calib_` steers, `calib2_` is only logged

The heading comes from the control board's BNO055 compass (`ImuData.euler_x`, IMU yaw), whose zero is not
north. To compare it with GPS azimuths, `plannerTick()` converts it with a calibrated offset:
`yawc = imu_yaw - calib.yaw + calib.azimuth` (calibrated yaw, 0 = north). `calib.azimuth - calib.yaw` is
the offset GPS course − IMU yaw — a mounting constant of the robot, not magnetic declination.

* **Two instances of the same `calibProcess()`:**
  * **`calib_` (`calibProcess1`) is the only one navigation uses.** With `-cg <gps_azimuth> -ca <imu_yaw>`
    (`calib_gps_azimuth`/`calib_imu_yaw` in `_full_launch.sh`, always `300`/`0`, i.e. offset −60°),
    `calibInit()` sets `ok=1` at startup, so the robot never stops to calibrate and the values stay as
    given. It re-calibrates only after 12 000 000 ms (3.3 h) — a `planner_node` running longer without a
    restart would start a real calibration (state `CALIBRATION`) and overwrite the constants.
    Without `-cg`/`-ca` it calibrates on the first suitable straight and its result *is* used.
  * **`calib2_` (`calibProcess2`, `ISTRO_CALIB2`)** re-calibrates every 120 000 ms and is referenced nowhere
    else — a monitoring stream only. Every `"calibration finished!"` seen during a drive with `-cg`/`-ca`
    comes from it.
* **What a calibration needs** (both instances): `nav_angle` within ±35°, more than `CALIB_NAVP_DIST1`
  (20 m) before the next navigation point and `CALIB_NAVP_DIST2` (15 m) past the previous one, no
  obstacle, no loadarea wait. `calib2_` also needs steering within 85-95° (`CALIB_PROCESS_ANGLE_MIN/MAX`).
  Then for `CALIB_TIME3_FINISH` (7 s): GPS speed ≥ 0.2 m/s and `ircv500` ≥ 5 from 2.5 s on, and GPS course
  spread ≤ 15° and yaw spread ≤ 5° from 3.5 s on. Any failure logs `"calibration interrupted!"` with the
  reason. In park drives almost every attempt ends on the steering check, so finished calibrations are rare.
* **The logged result is one instant**: `calib.azimuth` = the GPS course and `calib.yaw` = the IMU yaw at
  the 7 s mark, logged as `calib.delta = azimuth − yaw`. GPS course updates at 1 Hz and is noisy, so a single
  result scatters about ±10°. The per-tick `"calibration in progress..."` lines (TRACE) carry `gps_course`,
  `yaw`, `gps_speed` and `ircv500`, which allows averaging whole straight segments instead.
* **Offline check**: `script/log/calib_analyze.py LOGDIR…` prints the configured offset per run, a `WARN` for
  any `calibProcess1` activity while `-cg`/`-ca` are set, each `calib2_` result against the configured
  offset, the straight segments ≥ 4 s passing the checks above (`-v`), and a per-run/total verdict from their
  median. Field results for the configured −60°: `doc/260912_test_sadJK/README.md` §12.

### Wheel encoder (`ircv500`) — why speed and distance from it cannot be trusted yet

The E-Maxx wheel encoder is a single-channel Hall sensor counted by the control board. Each `R:` frame carries
the pulses since the previous frame (`ServoData.ircv`), and `ctrlboard.cpp` `ircth_get()` turns them into
`ircv500`, the pulses in the last 500 ms (interpolated, so fractional). There is no direction: the sign is
taken from the commanded speed.

* **Where it is used today**:
  * `updateXY()` — robot speed for the local position: `ircv500 × UPDATEXY_SPEED_COEF` (0.03) m/s. Because
    `ircv500` counts half a second, that is **0.015 m per pulse**, although the constant's comment says
    "one impulse = 3 centimetres".
  * "moving vs standing" thresholds of 5: `CALIB_IRCV500_MIN_VALUE` (calibration), `WRONGWAY_IRCV500_MIN_VALUE`
    (standing time is not counted as driving the wrong way) and `WRONGWAY_BACKCHECK_IRCV500` (`drive_node`'s
    backward check).
  * **No speed regulation uses it** — neither the control board nor the PC closes a speed loop; the motor gets
    a setpoint (`ctrlb_velocity`) and nothing checks the resulting speed.
  * **The situational speed control is switched off by configuration.** `speedctlProcess()` would step the
    setpoint up on clear straights: `-vf2` after `SPEEDCTL_V2_TIME` (2 s) with a free path 2 m ahead,
    `-vf3` after `SPEEDCTL_V3_TIME` (4 s) with a free path 3 m ahead, and back to `-vf` near obstacles
    (`MIN_MAX`) and during calibration. It chooses setpoints only, never reading the encoder. The team gave up
    on driving faster on straights and slower near obstacles, so `_full_launch.sh` sets `velocity_fwd` =
    `velocity_fwd2` = `velocity_fwd3` (12), and every step lands on the same setpoint. The keyboard speed
    keys keep it that way: they shift all three by the same amount (`loopWaitKey()`, e.g. 12/12/12 → 15/15/15).
* **The pulse scale is not constant — two regimes, `low` and `high`.** While driving we observed that, for
  an unknown reason, the control board at times sends a much higher number of pulses for the same speed.
  Measured against GPS on straight driving (`script/log/odom_analyze.py`, legend
  `script/log/odom_analyze.md`), at the same GPS speed the encoder reports either:

  | regime | pulses per m/s | metres per pulse (GPS displacement) | vs the code's 0.015 |
  |---|---|---|---|
  | `low` | ~35-45 | ~0.023-0.027 | distance under-reported ~1.6× |
  | `high` | ~200-250 | ~0.006-0.008 | distance over-reported ~2× |

  Each regime lasts from seconds to minutes (e.g. more than 3 min in `high` in one run) and both appear in
  almost every drive. Inside one regime the pulse rate follows GPS speed well (correlation ~0.6-0.9); mixed
  together it hardly does (~0.1-0.5). **The cause is not known.**

  **The scale also depends on the gearbox.** The figures above are from the 2026-09-10/12 drives. After the
  gearbox was replaced (first drive 2026-09-17), `low` measures ~0.016-0.018 m per pulse — close to the code's
  0.015 — while `high` stays at ~0.006. Both regimes are still there, and that drive spent two thirds of its
  distance in `high`. So **a measured scale is only valid for the mechanics it was measured on**, and one
  constant still cannot serve both regimes (they are a factor of ~3 apart). Numbers per drive:
  `doc/260917_test_sadJK/README.md` § 6.
* **Consequences, until the cause is found and fixed:**
  * **distance and speed from the encoder are unreliable** — the local position (`process_x/y`) and the
    obstacle grid built on it are off by a factor that changes during a drive;
  * **the encoder must not be used to regulate speed** — a loop on `ircv500` would react to every regime
    switch as if the speed had changed 3-4×;
  * the "moving" thresholds mean ~0.25 m/s in `low` but ~0.07 m/s in `high`. They only separate standing from
    moving, so this matters less, but it is not a fixed speed.
  * **in `high` the local position also stalls.** `updateXY()` rejects `ircv500 > UPDATEXY_IRCV500_MAX` (100,
    "3 m/s" at the code's scale), which the `high` regime exceeds at ordinary driving speed (up to 130
    logged). It then returns without integrating, having already advanced its time stamp, so that stretch's
    distance is lost. The log line is misleading: `"error: ctrlb values not initialised!"`. Measured: 3.6-8.5 %
    of planner ticks per run, matching the share of telemetry above 100, and concentrated in the `high`
    stretches.
* **The local position is pure odometry.** `process_x/y` are written only by `updateXY()`, from `ircv500`
  and the compass; they are never reset to the GPS position. Legacy did reset them to the route-snapped
  `gps_x/gps_y` on every new fix, but that block is commented out in `istro_rt2025.cpp` ("skusime zakomentovat …
  ci budu chyby/skoky v lokalnej mape mensie"), and the port keeps it that way. So the encoder does not matter
  for navigation (`navigation_node` steers by the snapped GPS), but it does matter for the obstacle grid
  (`wmodel`), which stores and evaluates obstacles at `process_x/y`.
* **Separate observation — slow start at the same setpoint.** Sometimes the robot drives noticeably slower than
  usual although the setpoint is unchanged, typically for the first few metres. A physical push, or raising the
  speed with the keyboard (then possibly lowering it back), gets it to the normal speed. Example, 2026-09-12
  QR test: 0.30-0.42 m/s at setpoint 347 (11:01:41-54, normal is ~0.7-0.85), then 0.67-0.83 m/s after the
  speed keys. The encoder pulses followed the real speed there (`low` regime throughout). The likely
  explanation is that the motor does not get over some threshold at that voltage, and once it does it
  reaches the higher speed at the same setpoint. Not confirmed, and not the same thing as the `high` regime,
  which lasts minutes at normal speed. This is also why operators often leave a higher speed set for the whole
  drive — the 350/353 setpoints in the logs.
* **Checking a new drive**: `python3 script/log/odom_analyze.py <logdir>` — per-mode metres per pulse and
  correlations. A tape-measured straight that also records the regime is the decisive test for the true scale.

### Loading / Unloading — QR-supplied coordinates and the load switch

The competition run is: service area -> `*1` load -> `*2` unload -> `*3` service area (end). The
first three rows of `navigationPoint[]` (`navig_data.cpp`) are `*1`/`*2`/`*3` with `ANGLE_NONE`
coordinates on purpose — the organizers only reveal where those places are on the day, as a QR code
held in front of the robot.

* **A point with no coordinates makes the robot stop and scan.** The trigger is not the `*` in the
  name but the missing position: `loadareaProcess()` sees `gps_navp_azimuth >= ANGLE_OK` for the
  next point, sets `PROCESS_STATE_QRSCAN_COORD`, commands `VEL_ZERO`, and turns QR scanning on in
  `vision_node` (`publishVisionControl()`). On a successful scan it calls
  `publishNavigationPointSet()`; `navigation_node` writes the coordinates into `navigationPoint[]`
  and replans the route. From there it is ordinary navigation to an ordinary point.
  (`publishNavigationPointSet()` is the cross-process replacement for legacy's direct
  `navigation_point_set()` call — same process in the monolith, two nodes here.)
* **The load/unload wait fires on ARRIVAL, not on the scan.** `navp_loadarea` describes the point
  the robot has just reached; `navp_loadarea_next` the one it is heading for. `navigation_node`
  moves one into the other only when a point is passed (`navigation_node.cpp:239`, legacy
  `istro_rt2025.cpp:630`). So the sequence is scan -> drive there -> *then* wait, and
  `navp_loadarea` stays `NONE` for the whole leg in between. Reading a log of an aborted run, an
  all-`NONE` `navp_loadarea` means the robot never arrived, not that the area was missed.
* **What it waits for**: `NAVIGATION_AREA_LOADING` holds at `VEL_ZERO` until `ctrlb_loadd == 1`
  (a person has put the barrel on and flipped the switch); `NAVIGATION_AREA_UNLOADING` until
  `ctrlb_loadd == 0`. `ctrlb_loadd` comes from the control board in `ServoData`.
* **`*3` gets QR coordinates but never waits**, which is correct — the robot returns to the service
  area empty and the run ends there. It falls out of the same mechanism rather than being special-
  cased: `navigation_next_point()` sets `loadarea = idx` only for `idx == NAVIGATION_AREA_LOADING`
  (0) or `NAVIGATION_AREA_UNLOADING` (1), and `*3` is index 2. **The area constants ARE the array
  indices**, so the first two rows of `navigationPoint[]` must keep that exact order.
* **`*` points demand a closer approach** than ordinary ones: `navigation_approach()` returns 1 for
  them, which switches arrival from `NAVIGATION_DISTANCE_THRESHOLD` to the stricter
  `NAVIGATION_DISTANCE_THRESHOLD2` plus the cone-seek condition.

## Design Decisions for `planner_node` (resolved 2026-08-27)

1. **Vision dmap placement — pose at capture time vs. pose at message-arrival time: decided Option B (simplified).** In legacy, `capture_camera_thread` stamps `image_number`/`process_dir`/`process_ref`/`process_x`/`process_y`/`process_yaw` onto the `DataSet` slot **at the moment the camera frame is captured**, and this pose rides along through the entire vision pipeline so `wmodel.updateGrid()` places the obstacle data using the robot's position *when the photo was taken*, not "now". Since the measured NN round-trip is ~480ms, `planner_node` using its *current* pose when folding an incoming `VisionData` into `wmodel` (rather than the pose-at-capture) introduces a bounded position/heading error proportional to NN latency × robot speed — accepted as a **documented deviation from legacy**, not silently absorbed:
   - No changes to `CameraFrame.msg`/`camera_node`/`vision_node` — `VisionData.msg` carries no pose fields, `wmodel.updateGrid()` is called with `planner_node`'s own latest `process_x`/`process_y`/`process_yaw`/`process_ref` member state instead of a value carried alongside the image.
   - **Forward-looking design note (explicit user request, not yet scheduled work):** to make this reconsiderable later without re-deriving it from scratch, `planner_node` should keep a small rolling log/buffer keyed by `image_number` — its `process_dir`/`process_x`/`process_y`/`process_yaw`/`process_ref` estimate at each tick — so a future revision (if drift/misplacement turns out to matter in practice) can look up "what was our pose estimate around the time image N was likely captured" and feed real pose-correlation logic into the planner, without needing `camera_node`/`vision_node` changes to *start* collecting this data. Exact shape (in-memory ring buffer? logged? size?) is left for whenever this is actually revisited — noted here so the intent isn't lost.

2. **`Lidar::process()` — extracted into the shared `istrobtx` package, done.** `Lidar::process(const lidar_data_t*, int, DegreeMap&, int&)` was pure geometry (only touched the already-shared `lidar_defs.h`/`DegreeMap`) but lived in `istrorsx_hw/include/istrorsx_hw/istrobtx/lidar.h`, which unconditionally `#include`s `sl_lidar.h` (the whole Slamtec SDK), so `istrorsx_core` couldn't call it without also depending on the SDK. Resolved the same way `dmap.h`/`camera_types.h` were: moved as the free function `lidar_process()` into `istrobtx`'s `lidar_defs.h`/`.cpp` (merged with the pre-existing `lidar_types.h`, see the `istrobtx` section above); `connect`/`init`/`close`/`drawOutput()` (SDK-free too, but with no caller outside `istrorsx_hw`) stay in `istrorsx_hw`'s `lidar.h`/`.cpp`. Verified via a clean full-workspace rebuild (zero new warnings/errors).

3. **New-message shapes/names:**
   - The `process_dir`/`image_number`/`process_ref`/`process_x`/`process_y`/`process_backward`/`coneseek_stop`/`coneseek_intlen` bundle — `PlannerData.msg`, published alongside `DriveCommand.msg` every `plannerTick()` (same "driving-critical vs. everything-else" split as `VisionData`/`VisionDebugData`). **`image_number` decided: keep it, as a real published field** — not just a `save_node`-local counter — since it doubles as a cross-node log-correlation key (matching legacy's own use, "which processing session do these logs/files belong to"), and is the natural key for the rolling pose-log from decision #1 above once that's built.
   - The `navigation_point_set()` replacement — `NavigationPointSet.msg` (`navp_idx`/`latitude`/`longitude`), published by `planner_node`, subscribed by `navigation_node`. Closes the cross-process gap flagged when `navigation_node` was originally built.

4. **`wmodel` debug image (`wmgrid`/`wmgrif`) for `save_node` — corrected 2026-08-27, `planner_node` must NOT render these itself.** My original decision (`planner_node` calls `wmodel.drawGrid()`/`drawGridFull()` locally and publishes the finished image) was **wrong** — user caught it: `drawGrid()`/`drawGridFull()` are exactly the slow, blocking calls legacy deliberately keeps out of `process_thread`'s real-time loop, reserved for `save_thread` alone; that division must be preserved 1:1, not silently inverted just because it's more convenient for message design. Corrected design, matching `wmodel` now living in `istrorsx_core` for both nodes to share (see "Port scope" above):
   - `planner_node` owns one `WorldModel`/`WMGrid` instance, calls only `updateGrid()`/`evalGrid()` — never `drawGrid()`/`drawGridFull()`.
   - **Corrected again, 2026-08-27 (second correction)**: a continuously-published `WMGridSnapshot.msg` was still wrong, for a second, more fundamental reason the user identified — legacy `save_thread` doesn't have data pushed to it at all. It calls `threads.checkData(...)` **itself**, only at the moment it has decided to save something, which is precisely what lets it control its own overhead (`write_wmodel`/`save_wmodel`/`SAVE_PERIOD_WMGRIF` and friends are all *consumer-side* rate-limits). A `planner_node`-published topic inverts that: `planner_node` would pay the ~4MB serialization/publish cost on its own schedule regardless of whether `save_node` even wants a snapshot at that moment (or is running at all). This is the same push-vs-pull mismatch, not just a size problem — publishing it *less often* wouldn't fix the control inversion, only shrink it.
   - **Fixed with a ROS 2 service, not a topic**: `planner_node` hosts a service (proposed `GetWMGridSnapshot.srv`, empty request → response = the raw `g[2001][2001]` array + `grid_x0`/`grid_y0` + `WorldModel`'s `image_number`/`last_x0`/`last_y0`/`last_alfa`/`last_ref`/`last_angle`/`last_angle_min`/`last_angle_max`); `save_node` calls it **only** when it has independently decided to render+save (its own equivalent of legacy's `write_wmodel`/`SAVE_PERIOD_WMGRIF` gating — e.g. correlated with newly-arrived `LidarData.msg` events, or its own timer), exactly restoring legacy's pull semantics and consumer-controlled overhead. `save_node` owns its **own** `WorldModel`/`WMGrid` instance, populated fresh from each service response, and is the **only** place that ever calls `drawGrid()`/`drawGridFull()` — both can run off the one fetched snapshot (matching legacy: `wmgrid` and `wmgrif` are two different renders of the *same* momentary `wmodel` state, `wmgrif` just gated to a slower cadence within `save_thread`'s own logic, not a second fetch).
   - **This is a deliberate, narrow exception to this project's "messages, not services" convention** (established for `VisionControl`/`DriveCommand`/`NavigationData` etc.) — flagging explicitly rather than silently reintroducing services, same spirit as the `sensor_msgs/msg/Joy` exception to "no external ROS 2 packages". The distinction: every other cross-node interaction in this project is a continuous state/control flow where "most recent value" is what matters and a service's synchronous request/response would add nothing; this one is a heavy, on-demand, consumer-paced fetch — exactly the shape services exist for, and exactly how legacy `save_thread` itself behaved (a deliberate pull, not a subscription).
   - Still open: raw vs. compressed payload in the service response — recommend raw/uncompressed first (still closest to legacy's zero-serialization shared-memory read, and every call is now consumer-paced so the total volume is bounded by `save_node`'s own throttling, not `planner_node`'s publish rate), revisit only if actually measured to matter.

5. **Two `calib_process()` instances (`calib`, `calib2`, `ISTRO_CALIB2`)** — not a real design fork, just flagging so the port doesn't accidentally "simplify" this away: `calib2`'s result is genuinely never used to affect driving (its own legacy comment says so), it exists purely to keep a second, parallel calibration-quality log stream running. Both instances still need porting as real state (two `calib_t` members), matching the "port every compile-time-active variant" rule. In practice: with `-cg`/`-ca` given, `calib` (`calibProcess1`) is valid from the start and only re-calibrates after 12 000 000 ms of uptime (3.3 h), so every `"calibration finished!"` seen during a drive is `calib2`'s. `script/log/calib_analyze.py` checks a run's logs for exactly that (any `calibProcess1` activity is a WARN) and measures the configured GPS-course-vs-IMU-yaw offset against `calib2`'s results and the straight segments it samples.

## `save_node` (`istrorsx_core`) — Image/Debug-Data Persistence Node

**Built and end-to-end verified 2026-08-29.** Legacy source: `save_thread` (`istro_rt2025.cpp:3586-3769`), plus its helpers `saveImage()` (:3412), `save_readData()`/`saveNavMap()` (:3430-3518), `readDiskStats()` (:3539). Purpose (user's own framing): persist a throttled subset (2-3 images/sec, not the internal ~30fps) of what the perception nodes compute, for (a) online visualization (`telemetry_node`/frontend), (b) post-hoc driving-problem diagnosis, (c) future NN retraining on frames where the model underperformed. Deliberately CPU/disk-light — this is why legacy rate-limits so aggressively (`SAVE_PERIOD=250ms`, `SAVE_PERIOD_WMGRIF=10000ms`, `SAVE_PERIOD_NAVMAP=1000ms`, plus a `/proc/diskstats`-based IO backoff, all ported 1:1, `ISTRO_SAVE_DISKSTATS_ENABLE` confirmed active in this project's `system.h`).

**`save_node.hpp`/`.cpp` written, built, end-to-end tested with simulated messages (2026-08-29, redesigned same day after user review).** Structure: `saveTick()` is save_node's own tick, driven by its **own `rclcpp::WallTimer`** (`SAVE_TICK_PERIOD=50ms`), replacing legacy's blocking `threads.getData(THDATA_STATE_PROCESSED, THDATA_STATE_SAVING)` wait (itself paced by `process_thread`). **First version tied this tick to `PlannerDebugData.msg`'s own arrival instead — user caught a real design flaw**: that made save_node persist *nothing at all* whenever `planner_node` was down or hadn't started, even though `camera_node`/`lidar_node` data was still arriving and worth saving. Fixed by giving `saveTick()` its own timer; `cb_planner_debug()` is now purely a cache-setter like every other `cb_*` (`image_number`/`lidar_angle_min`/`max`/`stop`/`process_angle_min`/`max`). `SAVE_PERIOD` (250ms) remains the actual save-rate limiter, unchanged — the 50ms timer just needs to be frequent enough to reliably catch that window.

All inputs (`CameraFrame.msg` ×2, `VisionDebugData.msg` ×2, `LidarData.msg`, `DriveCommand.msg`, `GpsData.msg`, `NavigationData.msg`, `PlannerDebugData.msg`) are cached as plain members by their own independent subscriptions — no `DataSet` round trip, matching `vision_node`'s/`planner_node`'s own precedent for state with no other in-process consumer. **User caught a second real bug in the same review**: nothing cleared a cached input after it was actually saved, so an input whose publisher had stopped (or was simply slower than `SAVE_PERIOD`) would get silently *re-saved as if new* on every following tick — legacy never had this failure mode, since its own per-iteration `pdata` was inherently "only what's new" (a fresh dataset object each cycle, fields left empty unless a thread genuinely wrote something new that cycle). Fixed by clearing each cached `cv::Mat`/`lidar_data_` immediately after it's consumed (used for a save, or found stale/mismatched) at the end of `saveCameraGroup()`/`saveCamera2Group()`/`saveLidarGroup()`.

`GetWMGridSnapshot.srv` is called asynchronously (`async_send_request` + a dedicated `cb_wmgrid_snapshot()` response callback) — **necessarily async**, not a blocking call like legacy's same-process/same-thread direct `wmodel` access, since this project's single-threaded `rclcpp::executor` convention would deadlock on a blocking service call issued from inside another callback. `cb_wmgrid_snapshot()` reconstructs save_node's own `wmodel` directly from the response (`WMGrid::g`/`WorldModel`'s tracking fields are all public, confirmed via `wmodel.h`) and does the same wmgrid/wmgrif/navmap throttle-and-draw legacy does inline right after computing `write_wmodel=1`.

**Re-verified after the redesign**: published `CameraFrame`+`VisionDebugData`+`LidarData` to a running `save_node` **with no `PlannerDebugData` ever published** — `camera`/`vision`/`cdepth`/`lidar` all still saved correctly (lidar's `image_number`/angle bounds fell back to their `-1`"none yet" sentinel defaults, rendered as legacy's own `999999` filename fallback — no crash, no stall). Then waited past `SAVE_PERIOD` with no new input at all and confirmed **no spurious second `SaveEvent`** fired (the redesigned cache-clearing correctly suppressed the stale re-save the earlier version was vulnerable to). Both fixes confirmed working, zero leftover processes.

Camera/vision-debug correlation (per the `AskUserQuestion`-confirmed design): `saveCameraGroup()`/`saveCamera2Group()` only draw+save `vision`/`nnpred` once a camera frame with a matching `image_number` is found for the cached `VisionDebugData.msg`; `saveTick()` never resynchronizes a genuine mismatch. This went through two corrections after the first version (a single cached "latest" `CameraFrame`, cleared immediately on any mismatch) proved wrong in two different ways, both found via `test_save_node4` against a real `vision_node`+NN server rather than synthetic messages:
1. **Clearing on the first non-match was too eager**: a real NN eval routinely takes longer than one `saveTick()` period, so the single cached frame was gone by the time a legitimately-in-flight `VisionDebugData` for it arrived — `vision.jpg` could never be saved at all whenever eval took longer than ~50ms. First fix: keep the cached frame alive across ticks instead of clearing on mismatch.
2. **That fix was still wrong** (caught in review before it shipped): with only *one* cached slot, `save_node`'s own "pick whatever's freshest every `SAVE_PERIOD`" and `vision_node`'s own "process whatever's freshest when NN eval finishes" are two independently-paced samplers of the same fast `CameraFrame` stream — nothing guarantees they ever land on the same `image_number`, especially once `camera_node` publishes faster than `vision_node` can keep up (steady-state, not just startup lag: user's own example, camera arriving at ~2x vision's rate). A single slot could keep getting overwritten by frames `vision_node` structurally never processes, meaning `vision.jpg` might never save at all regardless of how long a timeout waited.

**Final design**: `camera_front_buffer_`/`camera_rear_buffer_` (`save_node.hpp`), a short rolling history of recent camera frames keyed by `image_number` (color image only, plus a cache timestamp) — pairing looks *backward* through this buffer for whichever specific frame `vision_node` actually processed, rather than comparing two independent "currently newest" picks. Entries older than `CAMERA_VISION_PAIR_TIMEOUT` (`save_node.cpp`, 600ms) are evicted and logged once each as a WARN ("camera image never paired with vision-debug data, discarding") — this is also what bounds a `vision_node` that has stopped publishing entirely (crashed): its frozen `vision_front_image_number_`/`vision_rear_image_number_` will simply never match a new buffer entry again, and each one quietly times out with a log line instead of piling up forever. A hard count cap (`CAMERA_BUFFER_MAX`, 48 entries) backstops the time bound against unbounded growth if `saveTick()` ever stalled — sized to stay above the ~18-frame worst case a real ~30fps camera stream would accumulate within the 600ms timeout window (with the dead-`vision_node` case in mind, where nothing drains the buffer early via a match), so it stays a true safety net rather than becoming an active limiter of its own; both the count-cap and timeout eviction paths log a WARN when they discard an unpaired frame, and both pushes are gated on `conf.useCamera` (matching where the buffer is actually drained). **The timeout value's own tuning went through two rounds**: 1000ms (a starting guess) proved too tight even under normal conditions — `test_save_node4` failed against this dev VM's CPU/ONNX `visionn_server`, traced to `model_predict()` alone regularly taking 1199-1324ms, discarding a real, healthy NN round trip before it could complete; raised to 3000ms to comfortably clear that. **User then deliberately tightened it back down to 600ms** (not a revert to the original problem) — this dev VM's slow CPU/ONNX inference isn't the number this bound should be tuned against at all: the real Jetson target needs vision processing down around ~20ms/frame, and 600ms is meant to reflect *that* real-time budget (generous headroom over 20ms for the rest of `vision_node`'s own pipeline and scheduling jitter, not this VM's software-only stand-in). Explicitly accepted: testing on this VM will now occasionally discard a slow `vision.jpg` pairing (some runs of `test_save_node4` may show the timeout WARN instead of a `vision` tag) — by design, not a bug to chase, since a frame that would miss a 600ms window on the real target represents a genuine processing-time regression worth surfacing, not something worth silently waiting out. The `camera`/`cdepth` tags' own save is unrelated to this buffer — still tracked by a dedicated `camera_front_saved_number_`/`camera_rear_saved_number_` (distinct from `save_camera_`/`save_camera2_`, pure `SAVE_PERIOD`-window throttles), so a frame doesn't get re-saved as `camera` again on every throttle-window reset. `saveNavMap()` drops legacy's separate "gps_raw" `aux_point_t` marker (`GpsData.msg` has no distinct raw/filtered lat/lon pair to plot a second point for — an earlier `gps_node` simplification, not new here) but is otherwise a 1:1 port, including save_node's own `gps_pt[]`/`gps_pt_cnt` rolling breadcrumb buffer (rebuilt from `GpsData.msg`, not shared with `gps_node`/`navigation_node`).

**Bug found and fixed during end-to-end testing**: `Vision::drawOutput()`'s own `drawEPWeight()` indexes `epweight`/`elweight` unconditionally up to `ELINES_COUNT` — legacy never calls it with these empty (a real `vision_thread`'s `eval()` always populates all four `VisionDebugData` fields together), but a synthetic/partial test message with `markers` non-empty and `epweight`/`elweight` still default-empty **crashed save_node with SIGFPE**. Fixed by extending the existing `!vision_*_markers_.empty()` guard to also check `!vision_*_epweight_.empty() && !vision_*_elweight_.empty()` before calling `drawOutput()` — cheap, and closes a real robustness gap ROS's independent-topic model exposes that legacy's atomic-struct pipeline never had to defend against. **Second bug found while building the test itself, not a save_node bug**: `VisionGui::drawMarkers()`/`drawEPoints()`/`drawEPMask()` index pixel coordinates calibrated for the real `CAMERA_FRAME_WIDTH`/`HEIGHT` (848×480, `vision.init()`'s own calibration) — a synthetic test image smaller than that segfaulted via out-of-bounds writes; fixed by sizing the test's synthetic camera frame to the real dimensions, not a code change.

**Verified end-to-end** (`script/test/`-style manual `rclpy` script, not yet promoted to a permanent `script/test/test_save_node.sh`): published simulated `CameraFrame`+`VisionDebugData` (matching `image_number`) + `LidarData` + `PlannerDebugData` to a running `save_node -- -nowait -lidar /dev/null`, confirmed `camera`/`vision`/`cdepth`/`lidar` all saved correctly and a `SaveEvent.msg` published listing them; separately started a real `planner_node -- -nowait` alongside it and confirmed the full async `GetWMGridSnapshot.srv` round trip — `handleGetWMGridSnapshot()` served the (empty, no real sensor data) snapshot, `save_node` wrote `wmgrid.png`/`wmgrif.png`/`navmap.png`/`navmap.kml` from it, all files confirmed present on disk. Zero crashes after the fix above; both test processes shut down cleanly, zero leftover processes.

**Bug found by the user visually inspecting `test_save_node1`'s own output**: `navmap.kml` correctly showed the GPS point (Sad Janka Kráľa test coordinates) and the route network, but `navmap.png` had no lines at all. Root-caused to a missing `navigation_init()` call: `navmap_init()`'s own `navmap_calcXY()` (and every later `navmap_draw()` call's own midpoint conversion) call `navigation_getXY()`, which silently returns `x=y=0` for *any* input until `navig_ref_latitude`/`navig_ref_longitude` (file-scope globals in `navig.cpp`) have been set by `navigation_init(&geoCalc)` — with every node's *and* the midpoint's XY alike collapsing to the origin, every `navMapSegment` line in `navmap_draw()` degenerates to a single point at the image's exact center, invisible against the background. `navmap_export_kml()` never hit this: it writes `navMapNode[]`/`navigationPoint[]`'s raw lat/lon straight to the KML, no XY conversion involved at all — exactly why the KML looked right while the PNG was silently empty. `istro_main_save.cpp`'s `initDevices()` had a comment explicitly justifying skipping `navigation_init()` ("save_node only needs the compile-time route graph, not navigation_node's own live route-matching state") — correct about live route-matching, but wrong about `navmap_calcXY()`/`navmap_draw()`'s own hard dependency on the same call. Fixed by adding `GeoCalc geoCalc;` + `geoCalc.init()` + `navigation_init(&geoCalc)` before `navmap_init()`, matching `istro_main_navigation.cpp`'s own ordering exactly (both files' `initDevices()` now call the same three functions in the same sequence, only `navigation_node`'s own live route-matching is what actually differs downstream). Verified via pixel-color analysis of the regenerated `navmap.png` (5 distinct colors present, including the segment-line and GPS-marker colors — previously just the flat background).

**Separately, in the same investigation**: `test_save_node1.py`'s own `wait_for_tag()` could be satisfied by a `navmap_png`/`navmap_kml` `SaveEvent` generated *before* the test's `GpsData` publish was even processed — `saveNavMap()` runs unconditionally on its own `SAVE_PERIOD_NAVMAP` timer regardless of GPS, so a pre-GPS tick's tag, already queued from before the publish, could let the test declare success without the reported file actually containing the just-published GPS point (confirmed happening once: `cb_gps()` never fired that whole run — a discovery-timing miss, this session's already-documented recurring hazard, `test_save_node1.py`'s `sleep(1.0)` being shorter than `test_save_node4.py`'s already-hardened `3.0s`). Fixed both issues: raised the sleep to `3.0s`, and clear the test node's own accumulated `events` list right after publishing so only a tag generated after the publish can satisfy `wait_for_tag()`.

**Not yet done**: a permanent `script/test/test_save_node.sh` (this round's verification was ad-hoc, in the scratchpad); real-camera/real-lidar/real-planner-decision-cycle verification (only simulated messages exercised so far); `save_node_run.sh` convenience script (missing, matching the gap every other node had until noticed).

**Two `readDiskStats()`/`SAVE_DEVICE_NAME` bugs found and fixed (2026-08-29), both surfaced by running on this dev VM, both would likely also affect the real Jetson:**
1. **Hardcoded `SAVE_DEVICE_NAME="mmcblk0p1"` (a Jetson eMMC/SD-card-specific literal) never matches any device on a dev VM** (`nvme0n1`/`sda`/`vda`, never `mmcblk0*`) — harmless functionally (see next point) but produced an `ERROR` log line on every single tick. **Fixed with dynamic detection, not a CLI override**: new `detectSaveDeviceName()` (`save_node.cpp`, not a legacy port) resolves the real block device backing `out/` once at startup — `stat("out/")`'s `st_dev` (major:minor) → `/sys/dev/block/<major>:<minor>` (a symlink the kernel always maintains to the device's real sysfs path) → the basename of that resolved path is exactly the same device-name string `/proc/diskstats` itself uses. Verified manually against this VM (`stat`+`readlink` by hand) before implementing, then confirmed the running node logs `device="nvme0n1p1"`, matching. Cached once in the constructor (`save_device_name_`), not re-detected per tick.
2. **`readDiskStats()`'s own field-count assumption was stale**: legacy's `fscanf("%d %d %80s %d %d %d %d %d %d %d %d %d %d %d", ...)` reads exactly 14 whitespace-separated tokens per iteration (2 ints + name + 11 stat fields) — the pre-Linux-4.18 `/proc/diskstats` format. This dev VM's kernel (7.0, but the same gap opened at kernel 4.18, and the real Jetson's JetPack 6 kernel — 5.15 — is affected too) has **20** fields per line (11 original + 3 discard-stats fields since 4.18 + more since). Since `fscanf()`'s conversions skip newlines like any other whitespace, they don't respect line boundaries — the very first line left 6 tokens unconsumed, desyncing every subsequent "device name" read from real line starts for the rest of the file, so it could never match any real device again (confirmed live: `detectSaveDeviceName()` correctly found `"nvme0n1p1"`, yet `readDiskStats()` still returned `-2` every time, isolating this as a second, independent bug). **Fixed by switching from `fscanf()` token-streaming to `fgets()`-per-line + `sscanf()`** — reads one full line into a buffer, then extracts only the needed leading fields from it; naturally immune to however many trailing fields a given kernel appends (past or future), since `sscanf()` simply stops once its own format string is satisfied. Confirmed working live: `diskstats_iop` changed from the permanent `-1` fallback (readDiskStats always failing) to real values (`0`, matching this idle VM's actual IO load), zero more `ERROR` log lines.

### Local-position track in `navmap.png`/`.kml` (not in legacy)

The navmap image and KML show two lines ending at the newest GPS fix:
* **red** — the last `GPS_POINT_NUM` (30) raw GPS fixes (`gps_pt_`, `cb_gps()`), as in legacy;
* **yellow** — the local position `process_x/y` over the same span, for comparing odometry with GPS.

How the yellow line is made:
* **Sampling:** `cb_planner_data()` subscribes to `/robot/planner_data` and stores `process_x/y` every
  `PROCESS_POINT_PERIOD` ms (1000), at most `PROCESS_POINT_NUM` samples (30, i.e. 30 s). Both constants live
  in `save_node.hpp` and can be raised. The history is cleared when `process_ref` changes, because the axes
  switch from raw to calibrated yaw.
* **Drawing only with calibrated axes:** nothing is drawn until `process_ref` is 1. From then on x ≈ east and
  y ≈ north, the same axes as `navigation_getXY()`.
* **Anchoring:** `saveNavMap()` places the newest sample exactly on the newest GPS fix (`gps_pt_[0]`,
  converted with `navigation_getXY()`). Every older sample keeps its offset in metres from the newest one and
  is converted back with `navigation_getLL()`. The yellow line therefore shows where odometry says the robot
  was, relative to where GPS says it is now.
* **Rendering:** `navmap_draw()`/`navmap_export_kml()` take the extra `aux_point_t` array as `paux3` and draw it
  as a yellow line (`lstyle4` / folder `auxLine2` in the KML).
* **Timing:** samples and fixes are not time-aligned — the newest sample is at most one period older or newer
  than the newest fix, which can shift the yellow line by up to about one period of driving.
* **Nothing is sent from `planner_node` beyond `PlannerData`**, which it already published every tick.

## `logp` / `telemetry_node` — Telemetry Backend for the Visualization Dashboard

**Round 1 built 2026-08-29: a faithful 1:1 port of legacy `script/logp.cpp`'s parsing/output mechanism only** ("nech funguje úplne 1:1 parsuje logy a vytvára txt" — user's own explicit scoping for this round). No ROS topics/services, no `SaveEvent.msg` subscription yet — see "Deferred to a later round" below for why that's deliberate, not an oversight.

Legacy source: `script/logp.cpp` (428 lines, plain C++, no ROS/opencv/istrobtx dependency at all — a fully standalone program, sharing no code with `istro_rt2025` itself) + `script/logp_{start,stop,restart,logtrunc}.sh` + `html/logp_request.js` (jQuery frontend, polls a JSON file every 1.5s, not ported). It tails the shared application log (`logout/istro_rt2026.log`), substring-matches 20 known patterns per line (9 image-save announcements + 11 other "interesting" log lines), and rewrites the latest match for each pattern into `.txt`/`.html`/`.json` files every 250ms; a static jQuery page reads the JSON and displays `<img>` tags pointing at `out/` (served by Apache on the ramdisk path). Older rotated logs get gzipped once a minute.

**This project's own logging convention already reproduces legacy's core assumption**: every ROS node here calls `LOG_CONFIG_LOAD("conf/log4cxx.xml")` and writes into the same shared `logout/istro_rt2026.log` (confirmed directly, repeatedly, across this whole port's testing — e.g. `istroSave::`/`istroVision::` lines from different processes landing in the same rotated file) — so legacy's "one big combined log" assumption holds even though each subsystem is now its own process, and `telemetry_node` needs no restructuring to keep reading it.

**Pattern audit — checked against real runtime `LOGM_*` output, not just source inspection** (the pattern text only ever exists in macro-generated log lines, e.g. `LOGM_DEBUG(logger, "saveImage", tag << "_image=\"" << name << "\"")` → `istroSave::saveImage(): camera_image="..."` — never literally in any `.cpp` file, so grepping `src/` for the pattern strings gives false negatives). 14 of 20 patterns matched the ported code verbatim, no change needed (message-text patterns like `"navigation point passed"`, and a few function names deliberately kept under their legacy name during earlier ports — `process_readData()`'s own comment: *"Legacy logs this under the 'process_readData' module name even though the call site is in process_thread -- kept as-is, so grepping legacy and ported logs side by side still lines up"*). The other 6 needed updating, all for the same systematic reason — legacy's snake_case function names became this port's own established camelCase method convention:

| `logp.cpp` pattern (legacy) | `telemetry_node.cpp`'s `kFindPattern[]` (ported) | Why |
|---|---|---|
| `process_thread(): process_angle` | `plannerTick(): process_angle` | `planner_node.cpp` renamed `process_thread` → `plannerTick` |
| `{"INFO","calib_process",-1,0}` | `{"INFO","calibProcess",-1,0}` | renamed to `calibProcess1` (`calib_`)/`calibProcess2` (`calib2_`) (+ numeric suffix, matched as a prefix) |
| `calib_reset` | `calibReset` | renamed to `calibReset1`/`calibReset2` |
| `{"INFO","wrongway_check",-1,0}` | `{"INFO","wrongwayCheck",-1,0}` | renamed to `wrongwayCheck()` |
| `wrongway_process` | `wrongwayProcess` | renamed to `wrongwayProcess()` |
| `loadarea_process` | `loadareaProcess` | renamed to `loadareaProcess()` |

The other 14 (all 9 image-save patterns, `gps_writeData(): fix=`, `process_readData(): process_change`, `navigation point passed`, `navig::navigation...`, `ControlBoard::write(): data="D`) matched unchanged.

**No `istro_main_<subsystem>()` scaffold** (`Config`/`Threads`/`DataSet`), unlike every other node — legacy `logp.cpp` never used any of that, so there's no `Config` to parse or `DataSet` to wire up; `main()` just constructs+spins+shuts down `TelemetryNode`. **One real gotcha found via testing, not by inspection**: `main()` still has to inline `LOG_CONFIG_LOAD("conf/log4cxx.xml")` (+`LOG_THREAD_NAME`/startup banner) directly, since that's normally supplied by whichever `istro_main_<subsystem>()` a node calls — without it, log4cxx has no appender configured for *any* `LOGM_*`/`LOG_*` call at all (`"No appender could be found for logger (telemetry)"`), silently swallowing every log line including the node's own diagnostics.

**Output location — user decision, `AskUserQuestion`**: legacy hardcoded `/var/www/html/ramdisk/out/...` (an Apache-served ramdisk path on the Jetson, not present in this dev setup or provisioned anywhere yet in this port). Made configurable via a ROS parameter (`output_dir`, default `"ramdisk/"` — a workspace-relative directory, sibling to `out/`/`logout/`, created automatically via `std::filesystem::create_directories()` if missing) rather than hardcoding either the legacy path or `out/` outright — settable at launch via `--ros-args -p output_dir:=...` once a real ramdisk/web-server setup exists. `LOG_FNAME` (the *input* log path) stays a fixed internal constant (`logout/istro_rt2026.log`) — unlike the output location, this is a stable project convention, not something that varies by deployment.

**Output format — user decision, `AskUserQuestion`**: ported all three of legacy `writeResult()`'s outputs (txt/html/json), not just txt — same underlying `findResult_[]` data, trivially cheap to serialize three ways, and "úplne 1:1" was read as covering the whole function, not just its txt half.

**`read_empty_`'s own non-reset behavior — deliberate design, not a bug (user correction)**: `read_empty_` (was `read_empty`) increments on every `fread()` that returns 0 bytes and is never reset on a successful read — only inside `resetState()` (was `init()`), itself only called from the various error paths. Initially mis-flagged in this port as a legacy bug being "kept 1:1"; the user corrected this: `fread()` returning 0 means either a genuine read error *or* simply being caught up to EOF with nothing new yet (the ordinary tailing case), and there is no way to tell the two apart from the return value alone. Given the log's own expected volume during real operation — hundreds of lines/second across every node — 10 *consecutive* empty reads (~2.5s at this node's own 250ms period) is itself already a meaningful signal that something is wrong (the file got rotated/truncated/replaced under it, or the whole application stopped), and the cheap, safe response either way is the same: close, reset, and re-read from the top next tick. Confirmed via direct testing (ran the node against a static log with no new writes; the `ERROR ... "read: error2: could not read from file!"` line appeared right on schedule, ~2.5s in) that this resolves within one tick even when nothing was actually wrong — the very next tick's own `do-while` re-reads the whole file in one pass and repopulates `findResult_[]` identically — so a viewer of `istro_rt2026_out.txt` never notices; it just re-syncs more often on this dev VM's much quieter test logs than it would against the real robot's own log volume, which is the environment being quiet, not the mechanism being wrong. Kept verbatim, correctly understood as deliberate self-healing rather than something to silently "fix."

**`read_cnt < 0` replaced with a real error check, `ferror(fd_)`**: legacy's own condition also had `(read_cnt < 0) ||` here, dead for `size_t` (always false) and dropped for that reason (see above) — but the user pointed out this slot in the condition was *meant* to catch a genuine read error, and asked whether something like `ferror()` could actually do that job instead of leaving it empty. It can: `ferror(fd_)`'s error indicator is set only by a real failed read, never by reaching EOF alone (`feof()` is the separate indicator for that) — the standard, correct tool for exactly this. Added as an extra (first-checked) condition alongside the unchanged `read_cnt > BUFFER_SIZE - buffer_cnt_`/`read_empty_ > 10`, with its own more specific error log (`strerror(errno)`) when it's the actual trigger. This is a real improvement over legacy, not a 1:1 port of anything — legacy's own `read_cnt < 0` could never have caught a genuine error either, so this closes a detection gap that existed in the original too, not just in this port.

**Verified end-to-end**: built clean; smoke-tested startup (confirmed `ramdisk/` auto-created, all three output files written from this session's own leftover `logout/istro_rt2025.log` content — `camera_image`/`vision_image`/`navmap_image`/`cdepth_image` all correctly extracted); live-tailing tested by appending two fresh lines to the log file (one new `lidar_image` save, one `wrongwayCheck()` line) while the node ran — both correctly appeared in the regenerated `istro_rt2025_out.txt`/`.json` within one tick, confirming the 6 corrected patterns actually work against real (if synthetic) matching input, not just theoretically.

**`logv.cpp`** (722 lines, also in `script/`) is a separate, one-off **offline** post-race analysis tool (hardcoded Windows paths + a specific archived race's log/image prefix) — not a live service, out of scope here, not further analyzed.

**Deferred to a later round, deliberately**: the online (`SaveEvent.msg`-fed, no log-tailing needed for the 9 image patterns)/historical (past-run database/replay) backend redesign this node is ultimately meant to become (see the user's own framing above this round's scope note) — this round is intentionally the *simpler*, log-tailing-only mechanism first, matching every other node's own "get the 1:1 port working, then redesign" sequencing in this project. `telemetry_node_run.sh` (workspace root) added, matching every other node's own minimal run-script convention (`ros2 run istrorsx_core telemetry_node`, no CLI args — this node has no `Config` to pass flags to).

## `istrorsx_bringup` — Whole-System Launch Package

**Built 2026-08-29.** A new `ament_cmake` package, no compiled code — `install()`-only for `launch/`. One launch file this round, `full.launch.py`, per user decision: brings up every `istrorsx_hw`/`istrorsx_core` node at once plus the external `visionn_server.py` NN process and (by default) `joy_node` for a real Xbox controller — the single-command replacement for running all 13 `*_node_run.sh` scripts (+ `visionn_server.py`) by hand.

**Design analysis done first** (matching this project's own "analyze, then confirm open decisions, then build" sequencing): read all 13 `*_node_run.sh` scripts plus the parked `homologation_node`'s own launch file (`doc/260823_homologizacia/src/istrorsx_hw/launch/homologation_bringup.launch.py`, never merged — uses external `sllidar_ros2`/`tf2` against this project's own rule — but its `arguments=[...]`-based pattern for passing legacy `Config` CLI args through a `Node` launch action is exactly right and reused here). Two things flagged as easy to underestimate, both resolved with an explicit user decision:

1. **Two incompatible configuration mechanisms across nodes**: almost every node parses legacy-style POSIX CLI args via `Config::parseArguments()` (`-cb /dev/ttyUSB0`, ...) — not ROS 2-native parameters — while `telemetry_node` (this session, round 1) uses a real `rclcpp` parameter (`output_dir`). The launch file has to bridge both: `arguments=[...]` for every `Config`-based node, `parameters=[...]` only for `telemetry_node`.
2. **Every node assumes its own process CWD is the workspace root** — `conf/log4cxx.xml`, `out/`, `logout/`, `sample/*.jpg`, `conf/vision_mask.png`, `ramdisk/` are all hardcoded *relative* paths, not resolved via `ament_index`/package-share lookups the way a "standard" ROS 2 package normally would be launchable-from-anywhere. Fixing this properly would mean touching `Config`/`save_node.cpp`/`telemetry_node.cpp`/vision's own calibration loading across both `istrorsx_hw` and `istrorsx_core` — **user decision: out of scope for this package**, `full.launch.py` instead requires the exact same thing every `*_node_run.sh` already implicitly requires (CWD = workspace root at invocation time), with a fail-fast sanity check (`conf/log4cxx.xml` existence, checked before anything else) giving one clear error instead of 15 separate cryptic per-node failures if that's not the case.

**Launch arguments** (all `--show-args` discoverable): `cb_device`/`cb2_device`/`lidar_device`;
`launch_xbox_controller` (+`xbox_deadzone`); `launch_visionn_server`; `visionn_server_variant`.

Three naming/behaviour decisions came out of the user's own review of the first version:
* **`launch_*`, not `use_*`** — `use_xxx` is the legacy `Config` module's own convention
  (`useCamera`/`useLidar`/`useAHRSystem`, parsed from the CLI), so reusing it for launch-level
  switches would read as if it were the same mechanism. These are unrelated.
* **`launch_xbox_controller`, not `launch_joy`** — `/joy` has two producers in this project (the
  standard `joy` package's `joy_node` for the Xbox controller, and `keyboard_node`), and a
  USB-cabled joystick may become a third. Naming the switch after the *topic* wouldn't say which
  device it starts; naming it after the device does.
* **`launch_visionn_server`/`visionn_server_variant`, spelled out in full** — `vision_node` (the ROS
  perception node) and `visionn_server` (the external Python NN process, double "n") are easy to
  confuse; an abbreviated `launch_visionn` invited exactly that.

**`launch_visionn_server:=false`** skips starting the NN server entirely and assumes one is already
running (started by hand via `script/visionn_<variant>_server/visionn_server_start.sh`, which
backgrounds it; on the Jetson `./_visionn_server_run.sh` in the workspace root does that for
`roadyolo-trt` and refuses to start a second instance). `vision_node` then just opens its usual TCP connection to port 7001, and the launch
neither owns nor stops that server. Also skips the startup delay below — there's nothing to wait for.
Practical benefit during testing: the server takes seconds to load its model, so leaving it up across
repeated launches makes the edit/restart cycle much faster.

**What's launched, matching each `*_node_run.sh`'s own arguments as the new `DeclareLaunchArgument` defaults** (`cb_device`/`cb2_device`/`lidar_device`, all overridable — a genuine improvement over the hardcoded `*_node_run.sh` scripts, not just a wrapper around them): `ctrlboard_node`, `gps_node`, `lidar_node`, `camera_node` ×2 (`name=camera_node_front`/`camera_node_rear`, `-camdev 0`/`1`, both with the same `LD_PRELOAD` `additional_env` the existing `camera_node_*_run.sh` scripts need — see `camera_node`'s own section for the `librealsense2`/DDS symbol-collision this works around), `drive_node`, `navigation_node`, `planner_node`, `save_node`, `telemetry_node`, `visionn_server.py` (`ExecuteProcess` running the selected variant's own `visionn_server_start.sh` with `VISIONN_FOREGROUND=1`, so the interpreter choice — venv vs system python — stays in that script and `ros2 launch` still owns the process; skipped entirely when `launch_visionn_server:=false`), `vision_node` (delayed via a 5s `TimerAction` after `visionn_server.py` — a pragmatic fixed delay, **not** a robust readiness check; this project's own test scripts hit real discovery-timing flakiness with sleep-based waits more than once this session, see `03_progress.md`, so this is flagged as a known limitation, not solved here — the delay is skipped when the server is pre-started), and `joy_node` for the Xbox controller (`launch_xbox_controller:=true` default, `xbox_deadzone` matching `xbox_controller_run.sh`'s own `0.05`).

**Two things deliberately excluded, both explained in the launch file's own module docstring**:
* `gpsd` — needs `sudo` (kill/restart a system daemon, socket cleanup), awkward/fragile from inside a launch file and a once-after-boot system step, not part of "bring up this ROS graph." Documented as a manual prerequisite (`script/gpsd_start.sh` first) — **`_full_launch.sh`** (workspace root, added right after this package, user-requested) is the actual one-command "start everything including gpsd" wrapper: self-locates to the workspace root (works from anywhere), runs `script/gpsd_start.sh` (own `sudo` prompts), then `exec`s `ros2 launch istrorsx_bringup full.launch.py "$@"` (any extra args pass straight through to the launch file's own `DeclareLaunchArgument`s). `--no-gpsd` skips the gpsd step entirely — needed on a dev VM with no real GPS device, since `gpsd_start.sh`'s own final `gpspipe -r -n 20` verification blocks waiting for real NMEA fixes that will never arrive.
* `keyboard_node` — **not launchable from here at all**, and the flag that once pretended otherwise was removed. It puts the terminal into raw mode and reads keypresses straight off stdin, and refuses to start without one (`isatty(STDIN_FILENO)` → `"keyboard_node needs an interactive terminal on stdin"`); `ros2 launch` gives its children no tty, so it dies immediately regardless of where in the sequence it's placed — verified empirically, not assumed, after the user asked whether launching it *last* would work. Since `keyboard_node_run.sh` already exists, the launch instead prints a startup banner naming the exact command to run in a second terminal.

**Real regression found and fixed during this package's own smoke test, unrelated to the launch file itself**: every single node failed to log anything at all (`log4cxx: Error parsing file [conf/log4cxx.xml] ... not well-formed (invalid token)`) — traced to `conf/log4cxx.xml`'s own comment (added earlier this session, the `EVENT_TAG` cross-reference note) containing a bare `--` inside an XML comment body, which the XML spec forbids (the string `--` must not occur within comment text, only as part of the `<!--`/`-->` delimiters themselves) — invalidating the whole file, not just that comment. Went unnoticed through several individual node smoke tests since that edit because none of them happened to print the log4cxx startup error to a terminal being watched closely; running *every* node together via `full.launch.py` made it immediately, unmissably obvious. ## Core Architectural Choices
1. **External Board Instance:** 
   * The `ControlBoard` instance is managed externally via an `extern ControlBoard ctrlBoard;` declaration in the legacy header file. 
   * *Reason:* This safely bypasses complex initialization sequences, port-opening orders, and global state constraints of the legacy library without forcing a rewrite of the underlying driver.
2. **Local Custom Message Generation:** 
   * Custom `.msg` files are compiled directly within the package using `rosidl_default_generators`[cite: 4].
3. **Control Loop & Telemetry:** 
   * A 5 ms periodic wall timer (`serial_read_cb` in `ctrlboard_node.cpp`) handles continuous sensor polling.
   * `serial_read_cb` calls `ctrlBoard.getServoData()` / `ctrlBoard.getImuData()` each tick.
   * When `getServoData()` reports new data (`res > 0`), it publishes `istrorsx_hw::msg::ServoData` on `/robot/servo_data`.
   * When `getImuData()` reports new data (`res2 > 0`), it publishes `istrorsx_hw::msg::ImuData` on `/robot/imu_data`.
   * It also writes the same readings into the legacy shared `DataSet` via `threads.setData()` (see the Threads/DataSet section below) — kept alongside the ROS publish calls, not a substitute for them.
   * For current implementation status / verification state of this feature, see `03_progress.md`.

## Legacy `istrobtx` Library & the `ISTRO_ROS2` Switch
* `src/istrobtx/` and `include/istrorsx_hw/istrobtx/` are a **trimmed-down port of a much larger legacy robot codebase** (camera, lidar, GPS, AHRS, vision-based navigation, competition-specific maps for events like Robotour/RoboOrienteering). Most of that functionality is not present in this package — only serial comms with the control board, config/CLI parsing, logging, and a shared-memory data-passing primitive were kept.
* The compile-time switch controlling this is `ISTRO_ROS2`, hardcoded via `#define ISTRO_ROS2` in [system.h](../../src/istrorsx_hw/include/istrorsx_hw/istrobtx/system.h) (defined in **both** the `#ifndef WIN32` and `#else` branches, so it is effectively always on for this build — do not rely on it being conditionally toggled by CMake).
* Several `#ifndef ISTRO_ROS2` code paths (in `config.cpp`, `dataset.h`/`dataset.cpp`) reference headers that **do not exist in this repository** (`navig.h`, `dmap.h`, `lidar.h`). **Never remove or `#undef` `ISTRO_ROS2`** — the legacy branch is dead code kept only for diff-compatibility with the source project and will fail to compile if activated.
* When extending `Config` or `DataSet` with new fields, add them to the `ISTRO_ROS2`-defined branch (the second, smaller `class DataSet { ... }` block / the code *not* wrapped in `#ifndef ISTRO_ROS2`).

## Threads / Shared `DataSet` Pattern (legacy, mostly vestigial here)
* `Threads` (`threads.h`/`.cpp`) is a legacy pthread-based producer/consumer synchronizer: a fixed pool of `THDATA_NUM = 15` buffer slots, each tagged with a state constant (`THDATA_STATE_NEW`, `THDATA_STATE_SHARED`, `THDATA_STATE_CTRLBOARD`, ...), guarded by one mutex. `getData(state, state_new)` claims a buffer in `state` and atomically flips it to `state_new`; `setData(...)` returns it.
* In this package **only `threads.init()` is called** (from `initDevices()` in `istro_main_ctrlboard.cpp`) — `threads.start()` (which would spawn the original 9 pthreads for camera/lidar/vision/etc.) is never invoked. There are no legacy worker threads running; all serial I/O happens synchronously inside the ROS timer callback (`serial_read_cb`) on the ROS executor thread.
* Of the 15 preallocated `DataSet` slots, effectively **only one is meaningful**: one dataset is pinned permanently to `THDATA_STATE_SHARED` and used by `ctrlBoard_writeData()` in `ctrlboard_node.cpp` to stash the latest IMU/servo readings. `THDATA_STATE_CTRLBOARD` is also reserved but currently unused (no second reader/writer contends for the serial port). The rest of the state machine (camera/lidar/vision states) is inherited dead weight.
* **Practical implication:** `serial_read_cb` publishes directly to ROS topics right after the successful `getServoData`/`getImuData` calls — it does not route new data through the `Threads`/`DataSet` machinery to reach ROS, since nothing else in this package reads that shared state back out. The `ctrlBoard_writeData()` write-back into `DataSet` is kept alongside (harmless, preserves the legacy call shape) but is not required for the ROS publishers to work.

## `gps_node` — GPS Hardware Wrapper
* Separate executable from `ctrlboard_node` (own `main()`, own `istro_main_gps.cpp`/`.h` init scaffold, own `CMakeLists.txt` source list `GPS_NODE_SOURCES`) — see `05_migration_guide.md` for why.
* **`GpsDevice`** (`src/istrobtx/gpsdev.cpp`, `include/istrorsx_hw/istrobtx/gpsdev.h`), ported from `doc/istrobtx_2025/` unchanged. Interface: `init()`, `close()`, `getData(latitude, longitude, speed, course)` → `1` (valid fix), `0` (no fix, read OK), or negative (error).
  * Two backends, selected at compile time by `ISTRO_GPSD_CLIENT` (defined in `system.h`):
    * **`#ifdef ISTRO_GPSD_CLIENT` (active in this build):** connects to a locally-running `gpsd` daemon via `libgpsmm` (`localhost`, `DEFAULT_GPSD_PORT`) — does not touch the serial port directly. Requires `gpsd` to already be running and pointed at the real device (see `04_installation.md` § 6 and `<workspace_root>/script/`).
    * **`#else` (currently unreachable, kept intentionally):** a mock/replay backend that plays back static, hardcoded lat/lon/speed/course points instead of talking to real hardware, selected further by `ISTRO_MAP_*` macros. **Deliberately kept in the source** (unlike the dead `#ifndef ISTRO_ROS2` branches elsewhere, which exist only for diff-compatibility) — the intended future use is running/testing on a VM with no physical GPS attached, by flipping which branch is active. To use it, `ISTRO_GPSD_CLIENT` would need to be undefined for a build (not currently exposed as a toggle anywhere — doing so is future work, not yet wired up).
  * Excluded from `ctrlboard_node`'s build (needs `libgps` linkage `ctrlboard_node` doesn't have).
* **`GeoCalc`** (`src/istrobtx/geocalc.cpp`, `include/istrorsx_hw/istrobtx/geocalc.h`), also ported unchanged. Interface: `init()`, `close()`, `getDist(lat1,lon1,lat2,lon2, dist&, azimuth&)` (metres, degrees clockwise from north), `getCoord(lat1,lon1,dist,azimuth, lat2&,lon2&)`. Active backend (`ISTRO_GEOGRAPHIC_LIB`, defined in `system.h`) uses `GeographicLib`'s WGS84 `Geodesic` — needs `libgeographiclib-dev` (see `04_installation.md`). `gps_node` uses it to compute the distance/azimuth to the previous GPS fix (`gps_lastp_dist`/`gps_lastp_azimuth`) and a cumulative distance-traveled odometer (`total_dist`, log-only, not stored in `DataSet`).
* Neither `GpsDevice` nor `GeoCalc` need a CLI-supplied device path. `gps_node` still uses its own `Config`/`Threads`/`DataSet` scaffold (own instances, own `istro_main_gps.cpp`/`.h`, mirroring `istro_main_ctrlboard.cpp`/`.h`) — a deliberate choice to keep the legacy shape available for a future navigation node, not a functional requirement of `GpsDevice`/`GeoCalc` themselves.
* **`GpsNode::gps_read_cb()`** is the timer-callback port of the legacy `gps_thread` (200 ms wall timer — GPS fixes update at ~1 Hz, much slower than `ctrlboard_node`'s 5 ms). Active: `gps.getData()`, the `geoCalc`-based last-fix distance/azimuth and odometer, the `gps_pt[]` raw-position history (see below), `gps_writeData()`, and the `/robot/gps_data` publish. **Not yet migrated** (wrapped in `#if 0` / `NOT_YET_MIGRATED`-tagged blocks, see `05_migration_guide.md`): reference-point/local-XY conversion, next-navigation-point tracking, navmap route (re)planning, and reading `coneseek_stop`/`coneseek_intlen` from the vision/cone-detection subsystem — all genuinely navigation/vision-layer concerns needing `navig.cpp`/`navmap.cpp`/vision code that isn't part of this package.
* **`gps_pt[]`** (last `GPS_POINT_NUM` = 30 raw fixes, newest first) and its `aux_point_t` element type live in `istro_main_gps.h`/`.cpp`, mirroring how `gps`/`geoCalc`/`threads` are declared — even though `aux_point_t` is normally defined in `navmap.h` (not ported), the struct itself (`name`/`desc`/`style`/`longitude`/`latitude`, no other navmap dependency) was copied in directly rather than pulling in the rest of that header. Unlike the navigation-point/route fields, this is judged in-scope for `gps_node` itself (plain position history, not route/waypoint logic) — `initDevices()` in `istro_main_gps.cpp` seeds `gps_pt[0].style[0] = 0` exactly as the original did (including its own `// fixme` comment).
* `DataSet` (`ISTRO_ROS2` branch) only carries the fields `gps_writeData()` actually writes today: `gps_time`, `gps_fix`, `gps_latitude`/`longitude`(`_raw`), `gps_speed`, `gps_course`, `gps_lastp_dist`, `gps_lastp_azimuth`. The original class's `gps_navp_*` (next navigation point), `gps_ref`/`gps_x`/`gps_y` (local reference frame), and `coneseek_*` fields were deliberately **not** added yet — they belong to the not-yet-migrated navigation blocks above; add them (copying the original field shapes, per `05_migration_guide.md`) only when that logic actually gets ported.
* `/robot/gps_data` is published from `gps_latitude_raw`/`gps_longitude_raw` (the raw sensor reading), not `gps_latitude`/`gps_longitude` — in this reduced port the two pairs are always identical (no route-matching happens), but the message is defined to mean "what the GPS hardware reported," so it publishes the `_raw` fields on purpose, to stay correct even once a future navigation node might make the two diverge.

## `lidar_node` — RPLIDAR Hardware Wrapper
* Separate executable from `ctrlboard_node`/`gps_node` (own `main()`, own `istro_main_lidar.cpp`/`.h` init scaffold, own `CMakeLists.txt` source list `LIDAR_NODE_SOURCES`), following the same pattern as `gps_node` — see `05_migration_guide.md` for why.
* **`Lidar`** (`src/istrobtx/lidar.cpp`, `include/istrorsx_hw/istrobtx/lidar.h`), ported from `doc/istrobtx_2025/`. Interface: `init(portName)`, `close()`, `checkHealth()`, `getData(lidar_data_t*, data_cnt&)`, `process(...)` (fills a `DegreeMap` from raw scan data), `drawOutput(...)` (debug visualization, `ISTRO_GUI`-only). This class is deliberately hardware-independent at the interface level — the legacy project swapped its *implementation* between an RPLIDAR backend (`lidar.cpp`, `#ifdef ISTRO_RPLIDAR`) and a SICK TIM571 backend (`lidar_tim571.cpp`, a separate, not-yet-ported file, out of scope for now) without changing callers.
* Only `lidar.cpp`/`lidar.h` were ported — `lidar_rplidar.cpp`/`.h`, also present in the legacy source dump, are unused duplicates (the legacy `CMakeLists.txt` never compiled them; `lidar_rplidar.h` is byte-identical to `lidar.h`) and were not carried into this package.
* RPLIDAR SDK: the current Slamtec SDK (v2.x, `sl::` namespace) replaces the old free-standing `RPlidarDriver`/`IS_OK`/`IS_FAIL` API (SDK v1.6.1, what the legacy code was written against). Built from source into `/usr/local/rplidar_sdk` via `script/install/rplidar_install.sh` (see `04_installation.md` § 4/§ 6) — no apt package or `pkg-config`/CMake config exists for it, unlike `libgps`/`libgeographiclib`, so a future `lidar_node`'s `CMakeLists.txt` will need to reference its include/lib paths directly.
* `Lidar` gained an `IChannel * channel` member (`lidar.h`) alongside `ILidarDriver * drv` — the new SDK connects via a caller-owned channel object (`sl::createSerialPortChannel()`) instead of `init()` passing the port/baudrate straight to `connect()`; `close()` frees both.
* `init()` calls `drv->startScan(false, false)` — `useTypicalScan` **must** be `false` on this hardware (an RPLIDAR A1 running firmware 1.15, older than express-scan support added in fw 1.17). SDK v2.x's `getTypicalScanMode()` hardcodes `EXPRESS_SCAN` for any firmware lacking the `GET_LIDAR_CONF` protocol (fw < 1.24) regardless of actual device capability, so `useTypicalScan=true` sends an `EXPRESS_SCAN` command (0x82) this lidar silently doesn't answer — `connect()`/`getHealth()` still succeed (older commands), but `grabScanDataHq()` then spins with no data. SDK 1.12.0 used to check this via `checkExpressScanSupported()` and fall back to plain `SCAN` (0x20) automatically; that fallback was removed in SDK v2.x, so it's forced explicitly here instead.
* `getData()`'s conversion from the SDK's `sl_lidar_response_measurement_node_hq_t` scan nodes to the project's own `lidar_data_t` (`sync`/`angle`/`distance`/`quality`) preserves the exact value ranges (angle in degrees, distance in mm, quality 0-63) the original SDK v1.6.1-based code produced, so the `LIDAR_QUALITY_*`/`LIDAR_DISTANCE_*` thresholds in `lidar.cpp` (obstacle-avoidance/stop distances, quality filtering) remain valid unchanged.
* `process()`/`drawOutput()` (the `DegreeMap`-filling and OpenCV debug-drawing logic) have no SDK dependency and were left untouched. `drawOutput()` (`ISTRO_GUI`-only) has two pre-existing OpenCV3→4 incompatibilities (`CV_FILLED`, `CV_FONT_HERSHEY_DUPLEX`, both renamed in OpenCV4) not yet fixed — irrelevant unless/until `ISTRO_GUI` is actually enabled.
* **`DegreeMap`** (`src/istrobtx/dmap.cpp`, `include/istrorsx_hw/istrobtx/dmap.h`) — the fixed-size 0–180° obstacle map `Lidar::process()` fills from raw scan data. Ported unchanged; no further legacy dependencies beyond `logger.h`.
* `DataSet` (`dataset.h`) unconditionally `#include`s `lidar.h` (needed for the `lidar_data_t lidar_data[LIDAR_DATA_NUM]` member, present in `DataSet` since it's shared by all three executables) — since `ISTRO_RPLIDAR` is a global `system.h` switch, not per-target, `ctrlboard_node`/`gps_node` transitively need the rplidar SDK's include path too even though they don't link its library (same situation as OpenCV headers, see `04_installation.md` § 4). Only `lidar_node` actually links `RPLIDAR_SDK_LIBRARY`.
* **`LidarNode::lidar_read_cb()`** captures a full scan on a 50 ms wall timer — much tighter than `gps_node`'s 200 ms, since `lidar.getData()` (`grabScanDataHq()` underneath) itself blocks for the duration of a full 360° scan (roughly 150-200 ms with this hardware's forced legacy scan mode, see the `startScan()` note above), so the timer period is deliberately shorter than that and capture ends up effectively back-to-back, paced by the blocking call itself — the same way the original `capture_lidar_thread()`'s `while` loop had no artificial sleep of its own.
* **Not a line-by-line port of `capture_lidar_thread()`** (unlike `gps_thread`/`ctrlBoard_thread`, which were): the legacy function claims a dataset slot via `threads.getData(THDATA_STATE_NEW, THDATA_STATE_LIDAR_CAPTURING)`, handed off by `capture_camera_thread` (not its own timer), and reads vision/navigation pose state (`image_number`, `process_dir`, `process_ref`, `process_x`, `process_y`, `process_yaw`) via `capture_readData()` before capturing — none of which (`capture_camera_thread`, `vision_thread`, `process_thread`) is ported. `lidar_read_cb()` instead captures and publishes on its own timer (matching `gps_node`/`ctrlboard_node`'s pattern); the `capture_readData()`-equivalent block is present but wrapped `#if 0 // NOT_YET_MIGRATED` inside `lidar_read_cb()` — filling it for real needs a dedicated publish/subscribe link to a future camera node's current image number (see `03_progress.md` backlog), not just porting the call itself.
* **`lidar_writeData(lidar_data_cnt, lidar_data)`** (free function, mirrors `gps_writeData()`/`ctrlBoard_writeData()`) writes into the same always-available `THDATA_STATE_SHARED` `DataSet` slot those use — **not** the original `THDATA_STATE_NEW`/`THDATA_STATE_LIDAR_CAPTURING`/`THDATA_STATE_LIDAR_CAPTURED` pipeline states, since nothing produces/consumes those states in this ROS port. `DataSet`'s `ISTRO_ROS2` branch carries `lidar_data_cnt`/`lidar_data[LIDAR_DATA_NUM]` for this; `lidar_dmap`/`lidar_angle_min`/`lidar_angle_max`/`lidar_stop` (`Lidar::process()`'s output) are deliberately not added yet — no consumer reads them.
* `/robot/lidar_data` (`LidarData.msg`) is published every tick `lidar.getData()` succeeds, as parallel arrays mirroring `lidar_data_t` field-for-field (see `02_specifications.md`).
* **Bug fixed during the port:** `Lidar::init()`'s failure paths (`createSerialPortChannel()`, `connect()`, `checkHealth()`, `startScan()` all failing) `delete drv`/`delete channel` on error but must also null them out afterward — `close()` already did this, but the `init()` error paths initially didn't, leaving a dangling `drv` pointer. At the time this was found, `main()` constructed `LidarNode` and spun regardless of whether `istro_main_lidar()`'s `initDevices()` succeeded, so the very first `lidar_read_cb()` tick would call `lidar.getData()` through that dangling pointer and segfault — reproduced with `-lidar /dev/null` (a bogus device that fails `checkHealth()`). Fixed by nulling `drv`/`channel` after every `delete` in `init()`'s error paths, plus a defensive `if (!drv) return -1;` guard at the top of `getData()`. The fail-fast `main()` change (see § Init / Shutdown Split) now means this exact path — spinning after a failed `initDevices()` — can't happen in normal operation any more, but both fixes stay in place as defense in depth.

## `camera_node` — RealSense Camera Wrapper
* Two separate running instances of the **same** executable (front and rear camera), not two different executables and not one process owning both — the ROS2-idiomatic pattern for identical independent sensors (matches how official multi-camera ROS2 driver packages, including `realsense2_camera` itself, are deployed), unlike the legacy single-process app which ran `camera`/`camera2` together in one process. Own `istro_main_camera.cpp`/`.h` init scaffold, own `CMakeLists.txt` source list `CAMERA_NODE_SOURCES` — see `05_migration_guide.md` for the general pattern.
* **`-camdev <0|1>`** (`Config::cameraDeviceId`) selects which physical camera a given `camera_node` process binds to — a genuinely new CLI flag/`Config` field, since the original `Config` had no camera-selection parameter at all (`camera_node` didn't exist yet). `0` = "camera with lower serial number", `1` = "camera with higher serial number" (matches `Camera::init()`'s pre-existing `device_id` semantics); `-1`/omitted = any camera. The ROS node name (`camera_front_node`/`camera_rear_node`/`camera_node`) and topic name (`/robot/camera_front_data`/`/robot/camera_rear_data`/`/robot/camera_data`) are both derived from it at runtime in `camera_node.cpp`, since two simultaneously-running instances would otherwise collide on both.
* **`Camera`** (`src/istrobtx/camera.cpp`, `include/istrorsx_hw/istrobtx/camera.h`), ported from `doc/istrobtx_2025/` — `camera_opencv.cpp`/`.h` (an alternate, non-RealSense backend) intentionally **not** migrated. Interface: `init(dev_id)`, `close()`, `getFrame(Mat&)` (color, BGR8, resized to 640×480), `getFrameDepth(Mat&)` (depth, 16-bit, `CAMERA_DEPTH_FRAME_WIDTH`×`_HEIGHT`, active since `ISTRO_CAMERA_RS_DEPTH` is defined in `system.h`). No SDK version porting was needed — unlike `rplidar_sdk`'s v1.x→v2.x rewrite, the legacy code already targeted `librealsense2`'s modern `rs.hpp` C++ API, matching what's installed (2.58.3).
* `Camera::init()` fails fast if no matching device is found, checking the already-queried `rs2::device_list`'s size explicitly **before** calling `pipe.start()`: `device_id == 1` requires at least 2 devices present (the "higher serial number" pick only makes sense with two), any other `device_id` requires at least 1. This check was added during the port — see the `pipe.start()` bug note below for why it's necessary, not just a nicety.
* `camera_node.cpp`'s `main()` calls **`_exit()`**, not `return`, on every exit path (both fail-fast and normal shutdown) — see the process-exit-crash bug note below. This is a deliberate deviation from `ctrlboard_node`/`gps_node`/`lidar_node`'s plain `return`, specific to `camera_node`.
* **`CameraNode::camera_read_cb()`** captures on a 50 ms wall timer (color capture is requested at 30 FPS, ~33 ms/frame — the blocking `pipe.wait_for_frames()` call inside `camera.getFrame()` paces actual capture, same reasoning as `lidar_node`'s timer). **Not a line-by-line port of `capture_camera_thread()`**: same `THDATA_STATE_NEW`/pipeline-handoff issue as `capture_lidar_thread()` had (see `lidar_node` section above) — captures+publishes on its own timer instead. One legacy behavioral nuance *was* preserved: unlike `gps_thread`/`capture_lidar_thread` (fatal on their core capture failure), the legacy `capture_camera_thread()` treats `camera.getFrame()` failure as non-fatal (retries next iteration, doesn't set an error `result`) — `camera_read_cb()` matches this by logging the failure and ending the tick without marking `result` negative, so the per-tick exit log still reads `INFO exit(0)`.
* **`camera_writeData(camera_img, camera_depth)`** (free function, mirrors `gps_writeData()`/`lidar_writeData()`) stores `cv::Mat` objects **directly** into the `THDATA_STATE_SHARED` `DataSet` slot (not the original `THDATA_STATE_NEW`/`_CAMERA_CAPTURING`/`_CAMERA_CAPTURED` pipeline states) — safe and cheap since `DataSet` lives entirely within one process and `cv::Mat`'s copy is a shallow, reference-counted handle, not a pixel copy. `DataSet`'s `ISTRO_ROS2` branch carries `cv::Mat camera_img`/`camera_depth` for this — no `camera2_img`/`camera2_depth` pair, since each `camera_node` process now owns exactly one physical camera (unlike the legacy single-process app).
* **`CameraFrame.msg`** carries color **and** depth together in one message (`color_*`/`depth_*` field groups, not a nested sub-message) — deliberately not split into two topics, since `pipe.wait_for_frames()` already returns both synchronized from the same instant and splitting them would force a consumer to re-synchronize by timestamp. Each half's `cv_type` field is the literal `cv::Mat::type()` value (e.g. `CV_8UC3`=16 for color, `CV_16UC1`=2 for depth in millimeters), not a `sensor_msgs`-style encoding string — chosen so a consumer reconstructs a `Mat` in one line (`cv::Mat(height, width, cv_type, data.data(), step)`) without a `cv_bridge` dependency. `depth_width == 0` means depth capture failed/unavailable for that frame. A future switch to `sensor_msgs/msg/Image` (two topics, standard RViz/`image_transport` compatibility) is a known, deliberately deferred alternative — not implemented.
* **Known bug in `librealsense2` (`pipe.start()`) worked around, not fixed at the source:** with no device attached, `pipe.start(cfg)` blocks indefinitely instead of failing — confirmed via an isolated standalone test outside this project entirely, so it's `librealsense2`'s own behavior (most likely hot-plug-wait support), not a defect in this port. `Camera::init()` guards against it by checking the device count first (see above) instead of relying on `pipe.start()` to fail on its own. Temporary debug `LOGM_INFO` calls immediately before/after `pipe.start()` were deliberately left in `camera.cpp` (not removed) for fast re-diagnosis if this ever resurfaces.
* **Known crash on process exit, worked around via `_exit()`:** `librealsense2.so`'s own global destructors (`__do_global_dtors_aux`) segfault when the library is linked into the same process as `rclcpp`/DDS — confirmed via `gdb` backtrace (crash entirely inside `librealsense2.so`, zero `istrorsx_hw` frames) and ruled out as a pure `librealsense2` bug via two negative controls (a standalone `librealsense2`-only test, and Intel's own `rs-enumerate-devices` tool — neither crashes using the same installed library). `camera_node.cpp`'s `main()` calls `_exit()` on every exit path specifically to skip C++ static/global destructors and avoid this crash, rather than digging further into the exact library-interaction root cause.
* **Known crash at startup (distinct from the exit crash above), worked around via `LD_PRELOAD`:** `librealsense2.so` (for its DDS network-camera feature) bundles its own copy of `eprosima::fastcdr`/`fastrtps` and exports it globally (no hidden visibility) — this collides with ROS2 Jazzy's own `libfastcdr`/`libfastrtps`. When `CameraNode` registers its first ROS message type (in its constructor, before `rclcpp::spin()` ever runs), the dynamic linker can resolve the call into RealSense's differently-laid-out copy instead of ROS2's, corrupting the object and segfaulting — confirmed via `gdb` backtrace (`this` pointer in `FastBuffer::resize()` pointing into unrelated code). Worked around, not fixed at the source, by forcing the linker to prefer the ROS2 copies: `camera_node_front_run.sh`/`camera_node_rear_run.sh` both `export LD_PRELOAD=".../libfastcdr.so.2:.../libfastrtps.so.2.14"` before `ros2 run`. Anyone invoking the `camera_node` binary directly (not via these scripts) needs the same `LD_PRELOAD` or will hit this crash.

## `ups_node` — Waveshare UPS Power Module (C) Battery Telemetry
**Built 2026-09-11.** No legacy (`istro_rt2025.cpp`) equivalent at all — this hardware isn't part of
the original robot. Follows `keyboard_node`'s (`istrorsx_core`) precedent for a "new, no legacy
counterpart" node instead of `ctrlboard_node`/`gps_node`/`lidar_node`/`camera_node`'s pattern: no
`Config`/`Threads`/`DataSet`/`istro_main_X.cpp` scaffold, no `-nowait`-style CLI flags — a plain
`rclcpp::Node` with its own minimal `main()`. Lives in `istrorsx_hw` anyway (not `istrorsx_core`,
where `keyboard_node` is), since it's a real hardware sensor, matching that package's own purpose —
structurally closer to `keyboard_node`, semantically grouped with the other `istrorsx_hw` nodes.
* **Motivation**: a real-hardware test session hit a dead-battery failure with no way to have seen
  it coming (`03_progress.md`'s own milestone entry). This node makes battery voltage/current/power
  visible; deliberately **publish-only for now** — no low-battery warning/LED/safety logic yet
  (explicit user scoping), easy to add later once the topic exists.
* **`Ina219`** (`src/istrobtx/ina219.cpp`, `include/istrorsx_hw/istrobtx/ina219.h`) — a new class
  (not a port), reading the INA219 power monitor chip over I2C. Register addresses/calibration
  constants (`_cal_value=26868`, `current_lsb=0.1524`, `power_lsb=0.003048`, the 16V/5A
  calibration assuming a 0.01Ω shunt) and the `getBusVoltage_V()`/`getShuntVoltage_mV()`/
  `getCurrent_mA()`/`getPower_W()` interface are ported directly from Waveshare's own
  `/home/istrobotics/UPS_Power_Module_C/ina219.py` demo (`set_calibration_16V_5A()`) — verified to
  match it exactly, reading live: both report identical `bus_voltage`/`shunt_voltage`/`current`/
  `power`/`percentage` for the same instant.
* Uses the `I2C_SMBUS` `ioctl` (`<linux/i2c-dev.h>`/`<linux/i2c.h>`, kernel UAPI headers — no
  `libi2c-dev` or other new dependency) with an `I2C_SMBUS_I2C_BLOCK_DATA` transaction, which
  reproduces Python `smbus`'s `read_i2c_block_data()`/`write_i2c_block_data()` exactly: 2 raw
  big-endian bytes per register. This matters because it's **not** the same as the SMBus "word"
  ioctl transaction (`I2C_SMBUS_WORD_DATA`), which byte-swaps — using that instead would silently
  read every register backwards.
* **`UpsNode`** (`ups_node.hpp`/`.cpp`) — `declare_parameter`s `i2c_bus` (default `7`), `i2c_addr`
  (default `65` = `0x41`, matching the demo's own `__main__`), `poll_period_ms` (default `2000`,
  matching the demo's own `time.sleep(2)`); a wall timer at that period reads all four registers,
  derives `percentage` (`(bus_voltage-9)/3.6*100`, clamped — same formula/pack assumption as the
  demo), and publishes `UpsData.msg` on `/robot/ups_data`.
* **One deliberate difference from `keyboard_node`**: `main()` still calls
  `LOG_CONFIG_LOAD("conf/log4cxx.xml")` (confirmed this is a standalone macro call, not entangled
  with the rest of the legacy scaffold) so periodic readings land in the same shared
  `logout/istro_rt2026.log` every other node writes to (`istroUps::` logger category) — useful
  specifically for correlating a future low-battery brownout against other subsystems' logs, which
  `keyboard_node`'s interactive terminal output had no analogous reason to do.
* `full.launch.py`: its own `Node()` entry, own `ups_i2c_bus`/`ups_i2c_addr`/`ups_poll_period_ms`
  launch arguments wired to the matching ROS params — **no** `common_args`/`-nowait`, since none of
  those legacy flags apply to a node with no `Config`.

## Startup / CLI Arguments
* `main()` calls `istro_main_ctrlboard(argc, argv)` **before** constructing the ROS node, passing it the *raw* `argc`/`argv` (not ROS-arg-stripped). `istro_main_ctrlboard` → `Config::parseArguments()` scans these with plain `strcmp`, so ROS-specific args (`--ros-args ...`) are harmless but ignored.
* `ControlBoard::init()` (which actually opens the serial port) is only called if `-cb <device>` was passed and `conf.useControlBoard` is therefore true. **Without `-cb /dev/ttyXXX` on the command line, `ctrlBoard` is never initialized**, yet `serial_read_cb()` still calls `ctrlBoard.getServoData()` / `getImuData()` on it every 5 ms unconditionally — there is no guard checking `conf.useControlBoard` in the node. Always launch with `-cb <device>` (and typically `-nowait`, otherwise `waitForStart()` sleeps `conf.waitDelay` = 120 s by default before `main()` proceeds to spin the node), e.g.:
  `ros2 run istrorsx_hw ctrlboard_node -cb /dev/ttyUSB0 -nowait`
* `Config::parseArguments()` requires at least one CLI argument (`argc >= 2`) or it prints usage and fails — this applies to `gps_node` too, even though GPS has no device-path flag of its own. Launch it with at least `-nowait`, e.g. `ros2 run istrorsx_hw gps_node -nowait`.

## Runtime Configuration Changes — `ConfigUpdate` (`istrorsx_core`)
* **The problem the split created.** The legacy monolith had ONE global `Config conf` object, so when `loop_waitKey()` changed `conf.velocityFwd` (`istro_rt2025.cpp:4192`) the speed controller reading it in the same process (`istro_rt2025.cpp:2495`) saw the new value immediately. Here every node defines its own `Config conf;` (`istro_main_drive.cpp`, `istro_main_planner.cpp`, …), so that write stops at the process boundary. `drive_node` is the only node that mutates `conf` at run time, and it mutates exactly three fields (`velocityFwd`, `velocityFwd2`, `velocityFwd3` — `drive_node.cpp:684-690`); `planner_node` is the only node that reads them (`planner_node.cpp:1441-1503`).
* **The message.** `istrorsx_core/msg/ConfigUpdate.msg` on `/robot/config_update`, published by `drive_node` at the one place it already changes the config, consumed by `planner_node`'s `cb_config()` which writes straight into its own `conf`. Both sides log the change at INFO — deliberately, since it changes how fast the robot drives.
* **Delta, not snapshot.** A `bool update_velocity` says whether the `velocity_*` fields carry a change; a consumer ignores fields whose flag is false. Same shape as `istrorsx_hw/msg/SpeedCommand`'s `set_speed`/`set_steering_angle` and `DeviceAction`'s `display_text` — one message type, each consumer acting only on the parts it was told about. New runtime-mutable config gets a new flag plus its fields, not a new topic.
* **Default QoS, and no late-join recovery.** Depth 10, volatile — the same as every other topic here. The system starts all its nodes together (`full.launch.py`) and that is the only case this is designed for: a node restarted mid-run keeps whatever its command line gave it and will not learn about changes made before it came up. Deliberate simplification, chosen over `transient_local` latching so that nothing in this project depends on a QoS setting used nowhere else.
* **Rejected: a central config node.** ROS 1's parameter server was exactly that and ROS 2 dropped it on purpose (single point of failure, central daemon, node config belongs to the node). ROS 2's own replacements were considered and rejected too: `/parameter_events` is broadcast but `RMW_QOS_POLICY_DURABILITY_VOLATILE` (`rmw/qos_profiles.h:82`), so it solves nothing the plain topic doesn't; `parameter_blackboard` is a *demo* package (`demo_nodes_cpp`) and this project does not take third-party ROS packages; cross-node `set_parameters` needs the setter to know every target node by name and issue N independently-failing service calls. A dedicated config node earns its place only if a *second* node ever needs to change config (arbitration would then not belong in `drive_node`), or if config has to survive a full-system restart.
* **This is the third deliberate exception to "only our own legacy-derived messages"** — after `sensor_msgs/msg/Joy` for manual input. `ConfigUpdate` has no legacy counterpart because the monolith needed none.

## Control Board Write Pacing — and what it cannot fix

* **The board drops a command that arrives too soon after the previous one.** Legacy paced its
  writes (`setSteeringAngle()` + `msleep(5)`, `setSpeed()` + `msleep(5)`, `istro_rt2025.cpp:4524`);
  the port lost that and sent steering and speed in the same millisecond. `CtrlBoardNode::paceWrite()`
  restores it: called before every board write, it waits out the remainder of
  `CTRLBOARD_WRITE_GAP_MS` (10) and costs nothing when writes are already apart. Blocking
  `serial_read_cb()` while it sleeps is accepted — the board buffers telemetry.
* **KNOWN ISSUE — a lost command is never re-sent in `MANUAL`.** The periodic re-send
  (`VELOCITY_SET_PERIOD`) lives inside `controlTick()`'s `AUTONOMOUS` branch, and
  `velocity_change_`/`steering_change_` are one-shot flags, so a manual stop reaches the board
  exactly once. In `AUTONOMOUS` a dropped frame is corrected within 600 ms; in `MANUAL` nothing
  corrects it, and the robot keeps its previous speed until the operator presses the key again.
  The serial protocol has no acknowledgement, so pacing reduces the risk but cannot remove it.
  Measured before pacing: 8 of 13 stop commands ignored (`doc/ai/03_progress.md`, 2026-09-12).

## Init / Shutdown Split (`istro_main_ctrlboard()` / `istro_close_ctrlboard()`)
* `istro_main_ctrlboard(argc, argv)` only covers startup: logging config, CLI parsing, `initDevices()` (opens `ctrlBoard`), `waitForStart()`. It returns before any ROS node exists and does **not** close anything.
* `istro_close_ctrlboard(void)` covers shutdown: `closeDevices()` (closes `ctrlBoard`), final log message, `LOG_DESTROY()`. `ctrlboard_node.cpp`'s `main()` calls it **after `rclcpp::spin(node)` returns** (i.e. on actual shutdown — Ctrl+C/SIGINT triggers `rclcpp::shutdown()` internally, which is what makes `spin()` return), not before.
* This split matters: the original single-process legacy app's init function ran `closeDevices()` unconditionally right after its (now-empty) `loop()` stub — which, once ported as-is, meant `ctrlBoard.close()` fired **before** `rclcpp::spin()` ever started, so every `serial_read_cb()` tick would have been reading from an already-closed serial port (`fd = -1`). Any future node using this same `istro_main_<subsystem>`-style scaffold (e.g. `gps_node`'s `istro_main_gps()`/`istro_close_gps()`) must follow the same split — never call the shutdown function until after the node has actually finished spinning.
* **`istro_close_ctrlboard()` stops the robot before closing the port**: `setSpeed(VEL_ZERO)`, `setSteeringAngle(SA_STRAIGHT)`, `displayText("bye...")`, `sleep(1)` — ported from the tail of legacy's `loop()` (`istro_rt2025.cpp:4564`), which ran it after `threads.stop()` and before `closeDevices()`, the same position it has here. The board holds its last commanded value and nothing on it times out, so without this the robot keeps driving at whatever speed and angle it had when the software stopped. The `sleep(1)` is the point of the block: it gives the board time to act on all three commands before `ctrlBoard.close()` takes the port away. **This belongs to `ctrlboard_node`, not `drive_node`**, even though legacy issued it from what is now `drive_node`'s code — `drive_node` can only ask for a stop by publishing a `SpeedCommand`, and at shutdown nothing guarantees anything is left to deliver it. The last stop has to be written by whoever owns the serial port. Verified on the wire against a pty: `S2335\r\nS1334\r\nDbye...\r\n` after SIGINT.
* **All four `main()`s (`ctrlboard_node.cpp`, `gps_node.cpp`, `lidar_node.cpp`, `camera_node.cpp`) check `istro_main_<subsystem>()`'s return value and fail fast on non-zero**: they call `rclcpp::shutdown()` and exit immediately, without constructing the node, calling `rclcpp::spin()`, or calling `istro_close_<subsystem>()` (nothing was fully brought up to close — matches the legacy `istro_rt2025.cpp` `main()`, which also skipped `closeDevices()` on this path, see its `initDevices() < 0` branch). This means a device that fails to initialize (e.g. `Lidar::init()`/`GpsDevice::init()` against a non-existent/unresponsive device) now stops the node outright, rather than spinning forever with every tick logging the same failure. `camera_node.cpp` is the one exception in *how* it exits — it calls `_exit(1)` instead of `return 1`, to sidestep a `librealsense2`/`rclcpp` process-exit crash unrelated to this fail-fast logic itself (see `camera_node` section above). **Consequence for the placeholder-device smoke-test scripts** (`ctrlboard_node_run.sh`/`gps_node_run.sh`/`lidar_node_run.sh`, which all pass `/dev/null` for device paths not under test): `ControlBoard::init()` tolerates `/dev/null` (just opens the fd, no handshake during `init()` itself), so `ctrlboard_node_run.sh` still spins normally; but `GpsDevice::init()` (talks to `gpsd` during `init()`) and `Lidar::init()` (does `connect()`+`checkHealth()` during `init()`) do **not** tolerate a non-functional device, so `gps_node_run.sh`/`lidar_node_run.sh` now exit immediately with failure unless `gpsd` is actually running / a real lidar is attached — this is expected, not a regression. `camera_node` needs two invocations (one per `-camdev` value, for front/rear) rather than one — covered by two separate scripts, `camera_node_front_run.sh`/`camera_node_rear_run.sh`, instead of one parameterized script, matching the other three scripts' plain-one-liner style.

## Notes
* **Do not refactor `ctrlBoard` initialization into class constructors** without careful review, as it relies on an external instance (`extern ControlBoard ctrlBoard;`) declared in legacy headers.
* Some legacy code (e.g. local variable comments in `serial_read_cb`) still carries Slovak comments from the original source. New code should stay English-only per project convention; cleaning up old comments opportunistically is fine but not required.
* **Messages vs. services — the project default is messages.** Every cross-node interaction so far (`DriveCommand`, `NavigationData`, `VisionControl`, ...) is a continuous state/control flow, published regularly, where the most recent value is what matters — a request/response round-trip would add nothing. A node with complex internal state publishes a "brief" summary message about it on a regular cadence; that stays the default for any new cross-node interaction. Services are a **deliberate, narrow exception** — two kinds so far. First, `planner_node`'s `GetWMGridSnapshot.srv` (see decision #4), for state that is (a) genuinely live and too large/expensive to publish unconditionally at a useful rate, and (b) only ever needed on-demand by a consumer that must control its own fetch timing — mirroring how legacy `save_thread` pulled via `threads.checkData()` on its own schedule rather than having data pushed to it. Second, `navigation_node`'s `NavMapExport.srv`: a one-shot action triggered by an operator or a tool, with a success/failure result the caller has to see — there is no state flow for a message to carry. Before reaching for a service, check whether the state is actually static/compile-time (no ROS mechanism needed, just link the source directly if same-package) or reconstructible by the consumer from a message stream it already has (also no new mechanism) — see `05_migration_guide.md` § "Cross-Node Access to Complex/Large Internal State" for the full worked-out decision order and the `wmodel`/`navmap`/GPS-breadcrumb examples that motivated it.
